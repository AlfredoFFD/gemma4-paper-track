# Adapting Context Compression for Long-Horizon Agents with Counterfactual Continuations (PAIR)

- **arXiv:** 2609.36526 (cs.LG), v1, 29 Sep 2026. 41-page PDF (12 pages of body and references, 29 of appendix).
- **Authors:** Guanghui Min, Liang Wu, Minjia Shi, Yinhan He, Mayank Darbari, Liangjie Hong, Chen Chen (University of Virginia; Nokia).
- **Version read:** v1, arXiv HTML full text (4,030 lines) and all 41 pages of the PDF. Read Oct 28, 2026. Full text and PDF are kept outside the repo (copyrighted).
- **Leaned-on references, looked up** (abstracts, arXiv API):
  - ACON, Kang et al., ICML 2026 = arXiv 2510.00615. The prompt-adaptation baseline. It refines compression guidelines from contrasts between successful full-context and failed compressed trajectories, without fine-tuning; AppWorld, OfficeBench, multi-objective QA.
  - The authors' own predecessor, arXiv 2608.06503 ("Towards Reliable Context Compression for Long-Horizon Agents", v1 Aug 6, 2026; framework named TRACE). Its abstract already describes "paired closed-loop continuations from the same environment state" at individual compaction events, on AppWorld. **PAIR does not cite it.** So the same-state fork at a compaction boundary is public since at least Aug 6, 2026.
  - Zhang et al., ICML 2025 (failure attribution in multi-agent systems), cited for retrospective attribution; ReSum (2509.13313) and SUPO (2510.06727), cited as methods that retrain the agent; MEM1, cited only for the 8-objective QA task.

**One-line verdict:** the closest method neighbor for Claim B, outside code.
- It forks the agent from the same restored environment state at each realized compression boundary and continues from the pre-compression context (PRE) vs the post-compression summary (POST), with compression disabled afterwards, to termination (§3.2).
- The effect is scored as **outcome hazard** (drop in expected terminal reward) and **interaction burden** (extra remaining steps). Burden is common, severe harm is rare and localized (§3.3).
- The evidence is used to rewrite a structured (OpenClaw) compression prompt with the agent frozen. No training (§4).
- Two of its case studies are Claim B's two mechanisms in miniature (App. D.10): a summary that **wrongly records a result as settled** is followed into failure, and a summary that **reduces already-read documentation to prose** makes the agent re-read it (+5 steps).
- But: no code repository, no code graph, no inserted note on top of a summary, no controlled wrong entry, no true-vs-false comparison, terminal outcomes rather than the next action, frontier API models with unseeded sampling.

## Claim

1. **Compression degrades reliability before solvability** (§3.1, Fig. 1). On 90 AppWorld training tasks, smaller compression windows lower mean pass rate, but Pass^3 (solved in all 3 runs) falls much faster than Pass@3, and compressed runs take more steps.
2. **Burden is common, severe harm is sparse and localized** (§3.3, Fig. 2; App. D.2, Figs. 6–7). With m = 9 continuations per condition on 197 AppWorld boundaries (82 trajectories):
   - 151 of 197 boundaries lengthen the continuation, but only 12 add more than 5 steps and 3 add more than 10.
   - Only 11 boundaries cut continuation success by more than 0.5.
   - In the 15 failed trajectories, 43 of 67 boundaries leave success unchanged, 20 reduce it, 4 improve it; 11 of 12 failed trajectories with a harmful boundary have only one or two.
   - 27 boundaries in 22 *successful* trajectories reduce continuation success. So terminal outcome does not identify the harmful compression.
   - OfficeBench: 184 of 211 boundaries leave success unchanged. τ²-Bench Retail: 141 of 200.
   - Outcome hazard and burden are nearly uncorrelated (Spearman 0.004, 0.102, −0.054).
3. **A performance-difference identity** (Theorem 3.2, App. C.1): the gap between compressed and uncompressed expected reward equals minus the expected sum of boundary outcome hazards along compressed rollouts. It is a telescoping argument; it holds by construction when hazards are defined with compression disabled afterwards.
4. **PAIR improves reliability over prompt-adaptation baselines** (§5.2, Tables 1–2, 8).
   - AppWorld test-normal (168 tasks), history-only: PAIR 84.7 Acc / 79.8 Pass^3, vs no compression 84.1 / 78.6, unadapted OpenClaw prompt 78.6 / 68.5, ACON-UT 81.2 / 70.8.
   - Paired vs the best ACON variant (Table 8): AppWorld ΔPass^3 +8.9 [+3.0, +15.5] (sign test 22/7, p = 0.008) and +7.8 [+1.8, +10.7] (21/8, p = 0.024). On OfficeBench (n = 95) and τ²-Retail (n = 40) every interval includes zero.
5. **Transfer**: prompts adapted with GPT-5.6 Luna help MiniMax-M3 as agent and compressor (§5.3, App. D.8, Figs. 4 and 10), most under prefix-conditioned compression on AppWorld (79.6 → 84.1 Acc, 65.5 → 73.2 Pass^3).

## Method (enough to reproduce)

1. **Setting** (§2.1, Eq. 1). A frozen agent M. When the pre-compression context z̄ exceeds budget B, a compressor C (a frozen LLM with prompt P) replaces it with a summary c, |c| ≤ B. After compression the summary is the only record of the history.
2. **Boundary protocol** (§3.2, Def. 3.1).
   - Boundary state ξ_t = (h_{t+1}, z̄_{t+1}). Restore the *environment* state reached after h_{t+1}.
   - Continue from PRE (z̄_{t+1}) or POST (c_{t+1}) with the same agent and tools, compression disabled thereafter, to termination.
   - Q^R(ξ, x) = mean terminal reward of m continuations from context x; Q^L = mean remaining steps.
   - **Outcome hazard** H = Q^R(PRE) − Q^R(POST). **Interaction burden** B = Q^L(POST) − Q^L(PRE).
   - Diagnostic study: m = 9 per condition.
3. **PAIR** (§4, Fig. 3, Algorithm 1 in App. E).
   - Step 1: one trajectory per training task under the original prompt P0; keep every realized boundary.
   - Step 2: successive halving over 3 rounds; one PRE/POST pair per boundary per round; after rounds 1–2 only the top half by s = max(H/τ_H, B/τ_B) gets another pair (≤ 3 pairs). Keep boundaries with H ≥ τ_H = 0.5 or B ≥ τ_B = 5.
   - Step 3: an optimizer LLM sees PRE context, summary and continuation traces, diagnoses the defect, and revises only the guidance inside the fixed OpenClaw sections (Goal; Constraints & Preferences; Progress: Done / In Progress / Blocked; Key Decisions; Next Steps; Critical Context). Five candidate prompts.
   - Step 4: pick the candidate with the best pass rate on the 12 training tasks with the most compression events (ties: fewer steps).
4. **Models and budgets** (App. D.1). Agent, compressor and optimizer are GPT-5.6 Luna (OpenAI Responses API, reasoning effort medium; ≤ 2,048 output tokens per step; ≤ 8,192 per compression). Transfer: MiniMax-M3 via a hosted endpoint. Budget for the compressible history: 4,096 tokens (AppWorld, 8-objective QA), 2,048 (OfficeBench, τ²). The fixed prefix sits outside the budget, so peak inputs are 4–10K. Three runs "with different seeds"; the API sampling itself cannot be seeded, so PRE and POST continuations are independent draws, not common-random-number pairs.
5. **Baselines** (§5.1, App. F). No compression; FIFO; LLMLingua-2; Prompting (OpenClaw compaction prompts, quoted in full); ACON-UT and ACON-UTCO from the official repo. Two scopes: history-only, and prefix-conditioned (the compressor also sees the fixed prefix). Same trigger; the most recent turn is kept verbatim in every condition; rendered prompts hashed.
6. **Cost** (App. D.7, Table 7): 39.6–90.8M tokens per adaptation setting (ACON-UT 11.8–27.9M). Successive halving saves about 42% of continuations and 30.1% of tokens vs uniform 3 pairs.

## Metrics, exactly

- **Acc.:** mean task success over 3 runs. **Pass^3:** fraction of tasks solved in all 3 runs. **Steps:** mean interaction steps. **Peak:** peak input length (thousands of tokens). Cumulative tokens include agent and compressor.
- **Outcome hazard / interaction burden:** defined above (Eq. 3). With 3 pairs, H moves in steps of 1/3, so H ≥ 0.5 means an observed success-rate gap of at least 2/3.
- **Table 8:** paired bootstrap over tasks (10,000 resamples) and an exact two-sided sign test on the Pass^3 indicator.

## Results, including weak and negative ones

- **Main tables** (Tables 1–2, 4–6): PAIR has the best Pass^3 among compressed methods in all six benchmark–scope cells. On τ²-Retail it stays well below no compression (history-only 62.5 vs 72.5 Pass^3).
- **Significance is thin outside AppWorld** (Table 8): 4 of 6 intervals include zero. The pooled 75/34 count is descriptive only (scopes reuse tasks), as the authors say.
- **8-objective QA** (App. D.4, Table 5): PAIR history-only 39.3 EM vs Prompting 37.2 and no compression 40.9; prefix-conditioned 43.7. ACON-UT takes fewer steps (19.6 vs 27.0), which the authors attribute to retry and stop rules embedded in ACON's checkpoint ("plan steering"), not better compression.
- **Template control** (App. D.5, Table 6): locking ACON-UT to the OpenClaw sections leaves its history-only Pass^3 at 70.8 and raises prefix Pass^3 to 78.0; PAIR stays ahead (79.8, 80.4).
- **Sensitivity** (App. D.6, Figs. 8–9): with 3 continuations per condition, rank correlation with the 9-draw estimate is 0.69–0.76 for hazard and 0.81–0.89 for burden; selected-boundary overlap is 0.57–0.68. Successive halving: recall 0.82, precision 0.66 against the 9-draw selection. Thresholds varied one at a time keep Jaccard 0.56–0.83.
- **Case studies** (App. D.10, Table 9), each condition 3 compression samples × 3 continuations at the same restored state:
  - **Case A (outcome):** the P0 summary drops the "coworkers only" predicate and records "Use total 1676 as the answer". PRE 3/3 succeed; original POST 1/3 (two continuations submit 1,676 at once). Recompressed with P0: 3/3 summaries again say 1,676 and 3/3 fail. With the PAIR prompt the summary marks the total as unconfirmed and the coworker scope as tentative: 3/3 succeed. ACON-UT: 2/3.
  - **Case B (burden):** the P0 summary records that the login specs were read but reduces them to prose. All continuations succeed, but POST continuations reopen the documentation (4–5 doc calls): 14.0 vs 9.0 steps (B = 5.0). The PAIR prompt keeps executable signatures: 14.7 → 10.7 steps (PRE was 9.0).
  - Held-out traces (AppWorld test-normal): after a compression, the first action is a documentation lookup in 38% of ACON continuations vs 22% of PAIR continuations; 7.9 vs 5.9 documentation calls per task; 6.05 vs 4.74 steps to the next mutation. Descriptive, not paired.
  - **Negative cases, reported:** of 7 outcome and 6 burden boundaries replayed, 3 outcome defects did not recur under fresh P0 samples, 1 boundary still failed under PAIR, and 2 documentation-burden boundaries were not shortened. Only 3 outcome and 1 burden boundary meet the full replay criterion. Cases A and B were picked as the clearest.
  - The optimizer's first diagnosis of Case B was wrong (it blamed a verification step no continuation performed).

## Limitations

**The authors':** needs restorable environment states and full continuations from both contexts; cost grows with the number of boundaries and the remaining horizon; best suited to checkpointable or simulated environments; shifts in tasks or tools may need readaptation (App. A).

**Mine:**
- Frontier API models only; no small, open or quantized model. Sampling is not seeded, so each PRE/POST pair is two independent draws and noise is fought with repeats (m = 9, or ≤ 3 in PAIR itself).
- No software-repair task and no code graph. The environments keep state (AppWorld variables persist), so lost information can be re-fetched, which is exactly what burden measures.
- Outcomes are terminal reward and remaining steps. The next action is reported only as a descriptive rate on held-out traces (first action = documentation lookup, 38% vs 22%), not as a paired fork outcome.
- Case studies are selected and tiny (3 × 3), and 3 of 7 outcome defects did not recur under resampling.
- Very small budgets (2–4K of compressible history) chosen to force 2–3 compressions per task.
- The predecessor (2608.06503) is not cited, although its abstract describes the same paired same-state continuations.

**Assumptions it does not test:**
- That a summary's wrong entry is followed *because it is in the summary*, rather than because the PRE context also pointed there. There is no arm that swaps one entry for a false one while holding everything else fixed.
- That the agent would treat a true and a false entry differently. Discrimination is never measured.
- Whether adding information on top of a summary (rather than rewriting the summary) changes behavior.
- Whether the effects depend on model size or quantization.

| **A: a structured working memory keyed by code-graph nodes beats standard compaction under a small cap, no training** | partly (the generic half) | §4, §5, App. F.3, App. G | Structured, status-bearing checkpoints (Done / In Progress / Blocked; ACON's Execution Ledger and State Table with Verification rows: verified / failed / not run) under 2–4K budgets, with the agent frozen and no training, are compared against FIFO, token pruning and plain summarization. **What would make Claim B look like a straight application of PAIR:** reporting only "a note at the compaction boundary reduces re-reads". That is PAIR's interaction burden and Case B, moved to code (and Compact-Bench, 2610.31710, has already moved the with/without-compaction fork to SWE-bench repairs). The part PAIR leaves open is the controlled true-vs-one-wrong-entry contrast at the same state, scored on the next read or edit against the base rate.
