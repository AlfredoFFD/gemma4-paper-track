# Compact-Bench: Measuring What Context Compaction Costs Long-Horizon Coding Agents

- **arXiv:** 2610.31710 (cs.SE), v1, 22 Oct 2026, CC BY-NC-ND 4.0. 19-page PDF (8 pages of body, 11 of references and appendix).
- **Authors:** Ruopei Sun, Jianfeng Cai, Kangwen Zhao, Wengang Zhou, Houqiang Li (University of Science and Technology of China).
- **Version read:** v1, arXiv HTML full text (3,584 lines) and all 19 pages of the PDF. Read Oct 28, 2026. Full text and PDF kept outside the repo.
- **Why this paper was the second full read:** it is the only paper found that runs PAIR-style same-state continuations (full history vs summary only) inside **SWE-bench repairs**, i.e. Claim B's fork method in Claim B's domain. It appeared in the "context compaction coding agent" search and in PAIR's recommendation trail.
- **Leaned-on references, looked up** (abstracts):
  - "TRACE", Min et al. 2026 = arXiv 2608.06503, the PAIR authors' earlier paper (paired continuations from a restored environment state). Compact-Bench cites it but not PAIR (2609.36526).
  - COMPINT, Wang et al. 2026 = arXiv 2608.11242 ("Lost in Context Compaction"): side constraints survive compaction only 17% of the time; an inbox agent deleted emails without approval in 30/100 sessions after compaction vs 0 before.
  - Slipstream, Chen et al. 2026 = arXiv 2605.08580: validates a candidate summary against the agent's own continued reasoning from the same pre-compaction state; up to +8.8 points on SWE-bench Verified and BrowseComp.
  - The Complexity Trap = arXiv 2508.21433: observation masking matches LLM summarization in SWE-agent at half the cost.

**One-line verdict:** the fork-after-compaction method is already published for coding agents, so Claim B cannot claim the method; but nothing here inserts a note, plants a wrong entry, or scores the next action against a base rate.
- PRE continues from the cached full history, POST from the summary only, both from the same restored repository snapshot, scored by FAIL_TO_PASS tests (§3.1, Fig. 1).
- Damage (PRE passes, POST fails) ranges 5–64% of 22 repairs across 14 summarizer backbones (Table 2).
- Summaries keep the target file and most gold-patch tokens yet the continuation still fails; the loss is "progress", not facts (§4.4, Table 5).
- Repeated `read_file` calls after compaction are rare: at most one per condition in the four inspected failures (App. J, Table 15). Re-reading is not where the damage shows up here.

## Claim

1. **Summarizer choice moves damage from 5% to 64%** (§4.2, Table 2, Fig. 2). Claude Code prompt, Kimi-K3 continuation agent, 22 validated PRE-pass repairs. Stable damage (POST fails in ≥ 2 of 3 runs), Wilson 95% CI:
   - Claude Opus 4.8: 1 of 22 (5%) [1, 22].
   - Kimi-K3 and GPT-5.6-Luna: 4 (18%) [7, 39].
   - Middle of the range: GPT-5.6-Sol 6; Claude Fable 5 and 5.1, 8 each; GPT-6-Astra 9; Qwen3.8-Max, GPT-5.6-Terra and Claude Opus 5.5, 10 each; GLM-5.3 11; DeepSeek-V4-Pro 12; Hy4-Preview 13.
   - DeepSeek-Flash: 14 (64%) [43, 80].
   - 120 of 126 first-round damaged pairs are confirmed on rerun (App. B, Table 7).
2. **Prompt choice matters** (Table 3, App. F Table 13; Kimi-K3 summarizer, one run per case): POST passes 19/22 with the Kimi Code prompt, 18 Claude Code, 17 Gemini CLI, 16 Codex, 16 opencode.
3. **Retaining details is not preserving progress** (§4.3–4.4).
   - LLM summaries retain at most 16.0% of recurring structured details (paths, SHAs, error types…) vs 79.1% for a mechanical extractor (Table 4).
   - DeepSeek-Flash has the best retention (16.0%) and the worst damage (14/22).
   - In the four stable Kimi-K3 failures every summary keeps the target file; the pytest summaries keep 8/12, 10/12 and 5/5 audited gold-patch tokens (Table 5).
4. **Production compactions** retain 15.7% of future details at the first boundary (n = 106), 19.9% at the second (n = 27), then 4.9% (n = 6) and 1.8% (n = 1) (Fig. 3).

## Method (enough to reproduce)

1. **Tasks** (§3.2, App. E, Table 12): 35 localized SWE-bench repairs from pytest (18), sympy (6), xarray (3), pylint (3), requests (2), sphinx (2), flask (1); chosen for one test file, few FAIL_TO_PASS tests, median gold patch < 1 KB; base must fail and gold must pass in the per-instance venv.
2. **Phase A**: the agent works at most 10 steps; the history H and the working-tree snapshot D are cached and shared across methods and seeds.
3. **Continuations** (§3.1, Fig. 1): PRE gets H; POST gets only S = C(H). Same agent, tools and an 8-step limit; D is restored before each run; FAIL_TO_PASS tests judge. Outcome labels: preserved, damaged (PRE pass / POST fail), rescue (PRE fail / POST pass), unsolved.
4. **Agent** (App. G): Kimi-K3, thinking disabled, two tools (`read_file`; `run_command` with an allowlist), outputs truncated at 3,000 characters, file reads at 8,000; max_tokens 4,096 per turn. The task and continuation inputs are in Chinese; POST adds an English wrapper (App. L).
5. **Compression input** (App. G): every text block truncated to 2,000 characters and **every tool input or output to 200 characters** before summarization; transcript capped at its last 250,000 characters; output cap 6,144 tokens (Kimi-K3 runs) or 16,384 (cross-backbone runs).
6. **Repeats** (§4.1): first-round damage or rescue gets two more runs; for Kimi-K3 both PRE and POST are rerun, for other backbones only the summary and POST (PRE reused from the first run). The API gateway has no seed parameter, so "seeds" are independent server-side samples.
7. **Retention tracks** (§3.2–3.3, App. L): 146 never-compacted sessions (Kimi Code 73, Claude Code 50, opencode 14, other 9; 3 simulator-made), artificial boundary at request ⌊0.65n⌋; 106 sessions with ≥ 2 real compactions (224 boundaries, 140 scorable).

## Metrics, exactly

- **Damage rate:** damaged cases / PRE-pass cases (22). **Stable damage:** POST fails in ≥ 2 of 3 runs.
- **Recurring-detail retention** (§3.3): for session i, A_i = A(H_i) ∩ A(F_i), where A extracts distinct (type, value) pairs and F_i is the next 3–8 request payloads; score = matched pairs in A_i / |A_i| (case-sensitive substring in the summary), averaged over sessions.
- **Production-chain retention** R_{i,k}: share of details in the next ≤ 5 payloads found in the k-th production summary.
- **Repeated read** (App. J): an explicit `read_file` call on a file already read in Phase A; `sed`, `cat` and Python reads do not count.

## Results, including weak and negative ones

- **No rescues** anywhere in the 22-repair grid (Table 6): the summary never turned a PRE failure into a pass.
- **Six "variable" cases** (damage did not recur) are excluded from stable counts (Table 7).
- **The completed-write detector flagged zero boundaries** (App. C): the "summary calls a finished write pending" error was never observed with their patterns.
- **Harness validation** (App. D, Table 11): with separate directories, copied Phase-A paths sent POST commands outside the judged tree in 22 of 34 cases; two "damages" (xarray-6721, pytest-7521) disappeared once the directory was shared and restored. Interface artifacts can masquerade as compaction damage.
- **The sphinx-9230 trace** (App. I, Table 14): PRE reads the target, builds a reproduction and edits (8 actions); POST opens the right file, then greps and reads tests for 13 actions and never edits.
- **Repeated `read_file` calls** (Table 15): PRE 1, 1, 0, 1 vs POST 0, 0, 1, 1 in the four damaged cells.
- Prompt-comparison cells are single runs, with no intervals. The last-to-first retention ratio is 4.07 in a 20-session subset (App. C) while the per-boundary means fall after k = 2 (Fig. 3); with n = 6 and 1 at k = 3–4, both are fragile.

## Limitations

**The authors':** results depend on the tested repairs, continuation agent and budget; retention is literal string recurrence; later production boundaries rest on small, changing subsets; private session payloads and cached repair states are not released.

**Mine:**
- **The boundary is artificial and early** (≤ 10 steps), and the continuation gets only 8 steps. Slower recovery becomes failure, so "damage" mixes lost state with extra steps (PAIR separates these as hazard vs burden).
- **The summarizer is starved:** every tool output is cut to 200 characters before compression, so summaries cannot preserve code the agent read. This likely inflates damage and constrains the "summary keeps the target file but fails" diagnosis.
- **The arms differ by more than the history:** POST adds an English wrapper message to Chinese-language inputs.
- One continuation agent (Kimi-K3), 22 repairs, unseeded API sampling, PRE rerun only for Kimi-K3; no paired test between backbones; pytest-heavy.
- The repeated-read count covers only `read_file` in four failures, so it cannot show that re-reads are rare in general.

**Assumptions it does not test:** that adding information (rather than replacing history) would help; whether a structured or mechanical memory improves task outcomes (the 79.1% extractor is scored only on retention, never in Task Preservation); whether agents act differently on true vs false summary content.
