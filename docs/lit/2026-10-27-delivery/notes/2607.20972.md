# Delivery, Not Storage: Cue-Anchored Working Memory as a Harness Property for Coding Agents

- **arXiv:** 2607.20972 (cs.AI)
- **Author:** Swapnanil Saha (independent).
- **Version read:** v1, 23 Jul 2026, the only version on arXiv as of 2026-10-27. Read from the arXiv HTML text and the
  14-page PDF.
- **Abstract wording:** the arXiv metadata abstract paraphrases the PDF's. It says injection was delivered in every
  seeded run; the PDF says every *injection-equipped* seeded run (n = 3). The PDF is the accurate one: the seeded
  voluntary run (V) had no injection.
- **Artifacts:** transcripts, graders and audit logs are said to be at github.com/swapnanil/vectr. Not inspected.

## Claim

- **Thesis.** Memory for coding agents works only when the harness delivers it into context deterministically, at cued
  moments. A store the agent has to choose to query goes unused.
  - §2 frames lookup vs injection as the same content with a different delivery, and so a different cognitive role.
  - §5.2 says that knowledge sitting in a store contributes nothing by itself.
- **Key numbers:**
  - **Pull arm:** with a seeded store, memory tools and guidance but no hooks (arm V, n = 1), the agent made 0 memory
    calls in 114 turns (§5.2).
  - **Push arms:** injection was delivered in all 3 injection-equipped seeded runs (CS, H1, H2), with zero false-alarm
    fires over 40 and 35 audit-logged trigger evaluations in H1 and H2 (§5.3).
  - **Re-reads:** 24 of 61 intra-session re-reads (39%) re-fetched content the session had read before a compaction
    boundary (§5.5).
  - **Decay probe (§5.7):**
    - Facts held only in conversation were absent from 106 of 108 continuation summaries (arm N).
    - The injected store delivered all ten facts at launch and at all 138 compact-resumes, 139 deliveries in all
      (arm M), while M's final summary carried none.
- **Contribution as framed (§6):** no surveyed system combines all of the following:
  - per-memory standing triggers over {path, symbol, semantic, event, temporal};
  - deterministic evaluation by the harness;
  - memory the agent writes itself.

## Method

**Memory model (§3).** A memory is a tuple (content, kind, triggers, scope, decay).
- **Kinds:** directive, gotcha, finding, task, reference.
- **Triggers:**
  - path: a glob over touched files;
  - symbol: a named code entity is referenced; needs a code symbol graph;
  - semantic: similarity of current activity above a floor;
  - event: session start, prompt submit, pre-edit, pre-run, pre-compaction, post-compaction;
  - temporal: not-before, cooldown.

  Conditions are conjoined within a trigger and disjoined across triggers.
- **Default delivery by kind:**
  - directives at session start and after compaction;
  - high-priority task notes at session start, including every compact-resume;
  - findings through prompt-time semantic recall above a similarity floor.
- **Evaluation:** deterministic and harness-side. Every evaluation, fire and suppression is logged.
- **Delivery discipline:**
  - a two-tier budget: a compact index by default, full content on demand or for cue-anchored fires;
  - a per-session fire ledger that dedups repeats and resets at compaction;
  - a provenance frame on injected content (recorded by an AI session, not human-endorsed, verify);
  - a staleness check: if the anchored file changed after the note was written, the injection carries a warning.

  The similarity floor and budgets are not given as numbers.

**Implementation (§4).** Vectr, an open-source, local-first code-indexing daemon with a working-memory store, wired
into Claude Code in one of two ways. Both deliver the same store.
1. Native lifecycle hooks: session start, prompt submit, pre-tool-use, pre-compaction.
2. A transparent API proxy that injects into requests.

**Matrix evaluation (§5).**
- **Task:** one feature on a pinned Apache Camel checkout (~169k indexed chunks, SHA a543dc64): implement `reverse`
  for the stream-mode Resequencer EIP. The gate is an unmodified, fingerprinted acceptance test plus 42
  resequencer-scoped regression tests.
- **Held fixed:** the agent product, the model (Claude Sonnet 5), the prompt and the corpus SHA. Each run's launch
  posture is asserted and archived.
- **Seeds:** four exploration-grade notes covering locations, semantics and the guard site, never solution steps. One
  is a gotcha anchored to the file that contains the guard.
- **Arms:**

  | Arm | n | Store | Delivery |
  |---|---|---|---|
  | A | 3 | none | none |
  | B | 2 | cold store + tools + guidance | voluntary |
  | C | 3 | store + tools + proxy, cold store | injection, with nothing to inject |
  | CS | 1 | seeded store | proxy injection |
  | H | 2 | seeded store | native hooks |
  | V | 1 | seeded store | voluntary, hooks stripped (the control for H) |

  That is 9 pilot runs plus 3 native-channel runs. Six more launches did not reach grading; all are listed with a
  diagnosis.

**Decay probe (§5.7).**
- **Model and session:** Claude Haiku 4.5, one resumed session, with auto-compaction pinned at 100k tokens (the CLI's
  floor).
- **Workload:** one seeding phase, 16 exhaustive file-audit phases over a 64-file corpus, and a closing phase.
- **Facts:** ten synthetic facts, shown once in phase 0 in a fixture file that is deleted right after.
- **Constraints:** Read tool only, no shell, no subagents, restated in every phase. The closing phase requires writing
  the ten facts into the report.
- **Arms:**
  - N: no memory tier.
  - M: the ten facts stored as one-line notes, re-injected by the session-start and prompt-submit hooks at every
    compact-resume.
- **Read cap:** 8k (N) vs 6k (M); M's cap was forced down by the harness thrash guard.
- One gated run per arm.

## Setting, data, models

- **Data:** one repo (Apache Camel), one feature task in the matrix, one audit workload in the probe.
- **Harness and models:** the Claude Code CLI; Claude Sonnet 5 in the matrix, Claude Haiku 4.5 in the probe.
- **Context:**
  - matrix: not stated, but "~31.6k tokens (a sixth of a context window)" in §5.5 implies about 190k;
  - probe: compaction at 100k, with a per-read cap of 8k or 6k.
- **Code graph:** Vectr indexes code, and the symbol trigger needs a symbol graph, but no graded run ever fired a
  symbol trigger (§7).

## Metrics (exact definitions)

- **Correctness:** the acceptance test (byte-unmodified, fingerprinted) and the regression suite both pass.
- **Adoption:** the count of voluntary memory operations (writes, recalls) per run.
- **Mechanism:** injections, skips and false-alarm fires, from the proxy's status counters and the daemon's audit log.
  "False alarm" is not defined beyond a fire outside the cued moments.
- **Value:**
  - turns;
  - cost ($);
  - wall time in seconds (the transcript's duration_ms);
  - total tool calls;
  - grep/find calls.
- **Re-exploration:**
  - intra-session re-reads;
  - cross-compaction re-reads;
  - result tokens re-paid (chars/4);
  - re-exploration share of exploration calls.
- **Decay:**
  - verbatim presence of each fact token in every continuation summary (the "survival curve") and in the final report
    (the endpoint);
  - provenance forensics over the transcript and the audit ledger;
  - audit completeness: declaration recall against a regex ground truth over the 64 files.
- No statistical tests anywhere.

## Results, including weak and negative ones

**Correctness (§5.1).**
- 12/12 graded runs pass.
- Every run directory's sha-check line reads FAILED, because Camel's formatter re-wrapped two javadoc lines. The
  transcripts show zero agent edits to the test, and the canonical test was restored byte-for-byte before grading.

**Adoption (§5.2).**
- **B and C:** 0-1 voluntary writes across five runs, despite 32 memory-guidance mentions in the instruction files.
  The native auto-memory directory was never created.
- **V:** 0 memory calls in 114 turns.
- **CS:** the matrix's only memory-hygiene loop (recall by id, forget the now-obsolete gotcha, remember a completion
  note). It came after CS's first two voluntary calls timed out on an availability bug.
- **H1:** expanded all three injected index entries by id within seconds. Later, a semantic recall returned
  staleness-flagged notes, and the agent superseded the obsolete gotcha.
- **H2:** one semantic recall about 17 s in, then worked from the injected content without expanding it.

**Mechanism (§5.3).**
- **CS:** 262 API requests. 241 reached the injection decision: 5 injected, 236 skipped. 21 did not reach it (a number
  obtained by subtraction).
  - The daemon logged 6 PROACTIVE_INJECT events, one more than the proxy's count, and the discrepancy cannot now be
    reconciled.
- **H:**
  - A three-note index was injected at launch. The index budget dropped one of the four seeds, and the agent
    recovered that note's content from code exploration.
  - The gotcha fired on the agent's first touch of its anchored file (about 20 s and 7 min in). Later touches were
    suppressed, and the ledger re-armed at compaction.
  - Zero false alarms over 40 and 35 evaluations. My rule-of-three bound: pooled 0/75 gives a 95% upper bound near 4%
    per evaluation.
- **Replication caveat:** transcripts do not record prompt-submit or pre-tool-use hook payloads, so the audit log is
  the only evidence for those injections.

**Value (§5.4).**

The pilot compares vanilla runs (A, n = 3) with tool-equipped runs (B + C + CS, n = 6, store cold in 5 of the 6). The
authors say this prices the platform (semantic search plus guidance), not memory delivery.

| Metric | Vanilla (A) | Tool-equipped (B + C + CS) | Change |
|---|---|---|---|
| tool calls | 137.3 | 79.8 | -42% |
| grep/find calls | 48.3 | 22.2 | -54% |
| cost | $7.20 | $5.08 | paper: -30%; I get -29.4% |
| turns | 106.3 | 77.0 | -28% |
| wall | 2123.6 s | 1432.8 s | -33% |

The same-seeds comparison (knowledge held constant):

| Run | Delivery | Turns | Cost | Wall |
|---|---|---|---|---|
| H1 | hooks | 95 | $5.22 | 1454 s |
| H2 | hooks | 102 | $6.09 | 1187 s |
| V1 | voluntary | 114 | $6.23 | 1297 s |
| CS (pilot) | proxy | 106 | $6.57 | 1629 s |

- **The authors' own caveat:** within-arm wall spreads are 2.4-4.4x, nothing is significant, and a defensible
  percentage would need about 15-20 runs per arm.
- **My check:** §5.4 says the direction is consistent on every metric and both channels. Their own numbers do not
  support that.
  - H1 is slower than V1 (1454 vs 1297 s).
  - CS is costlier and slower than V1 ($6.57 vs $6.23; 1629 vs 1297 s).
  - Only turns favor all three injected runs over V1.

**Re-exploration (§5.5).** Over nine pilot transcripts:
- 61 intra-session re-reads, of which 24 (39%) crossed a compaction boundary;
- about 78k result tokens re-paid;
- a pooled re-exploration share of 10.9% (range 0-29.1%);
- the three heaviest runs hold 55 of the 61 re-reads and 21 of the 24 cross-compaction ones;
- four runs had zero re-reads;
- the worst run re-paid about 31.6k tokens.

**Single compaction (§5.6). Negative for the memory tier at this scale.**
- All twelve runs compacted at least once and finished green.
- One compaction was near-lossless for task continuity with or without the memory tier.
- What the tier added was staleness warnings on recall, supersession of the obsolete note, and re-armed triggers.

**Decay probe (§5.7).**

| | N (no tier) | M (injected store) |
|---|---|---|
| compactions | 108 | 138 |
| turns / cost | 1,235 / $21.26 | 1,489 / $28.94 |
| summaries with 10/10 facts | 2 (after an accidental re-surfacing) | 53 |
| summaries with 0/10 facts | 106 | 85 |
| summaries with a strict subset | 0 | 0 |
| first and final summary | 0/10 | 0/10 |
| endpoint | 10/10, invalid | 10/10, clean |
| fact-bearing deliveries | 0 | 139 |

- **N's endpoint was invalid.** The agent rebuilt the facts by grepping the harness's session files: 260 shell
  commands in all (38 fact archaeology, 152 corpus/orientation, 70 report). The first shell use came after 15
  summaries.
- **M's endpoint was clean.** There were zero fact-targeted shell commands.
- **M's 139 deliveries** sit within 157 logged evaluations: 139 deliveries, 16 zero-note fires, 1 non-seed note, and
  1 pre-launch probe.
- **Delivery cost:** about 240 tokens per delivery, about 34k in total.
- **M's broken rules:** 321 shell results despite the ban (one incidentally echoed fact tokens, more than 60 boundaries
  before the endpoint) and 3 forbidden subagents.
- **M's voluntary memory use:** 11 remember calls (9 landed) and 9 recalls.
- **The index tier fell short:** the prompt-submit index carried only 3/10 fact tokens early and 1/10 late.

Weak and negative results in the probe:
- **Visible content was still dropped.** M's first three summaries dropped the facts even though they had been
  injected into the context being summarized. Later, 72 consecutive summaries carried 0/10 while deliveries continued.
  Only re-injection kept the facts available.
- **M cost more:** +21% turns and +36% cost vs N.
- **M's audit was less complete:** 0.70 vs N's 0.93, confounded by M's 6k read cap vs N's 8k.
- **The thrash guard punished the memory arm.**
  - N: killed once (phase 6, after 49 boundaries).
  - M: the launch at 8k was scrapped after the guard killed the first audit phase 14 turns in; at 6k it still killed
    the final phase.
  - The reason: fixed per-cycle overhead (tool schemas, guidance, injections) reads as refill pressure.
- **The task state, which nobody seeded, decayed into confabulation:**
  - two audit phases skipped;
  - an invented phase numbering ("Phase 52: Files 203-206" in a 16-phase audit);
  - 37 archaeology greps;
  - two reads of the memory system's design document off the operator's disk.

  The summaries carried this false task model forward across boundaries.
- **In the pilot (k = 2),** a summary claimed all ten facts were maintained while carrying none of them.

## Limitations

**The authors' (§7).**
- **Construct:**
  - verbatim token matching;
  - synthetic facts with an explicit closing obligation, so the probe measures survival and delivery, not spontaneous
    use;
  - chars/4 token estimates;
  - regex-based completeness;
  - symbol and temporal triggers never fired, so the composition claim rests on 3 of the 5 trigger types;
  - capture is unevaluated, since the notes were seeded by the harness.
- **Internal:**
  - M's 6k vs 8k read cap is a confound;
  - tool bans proved unenforceable;
  - an 11-minute host hibernation;
  - the same person built the system and the benchmark harness (mitigated by pinned SHAs, fingerprints, archived
    launch assertions and published logs).
- **External:**
  - one corpus, one task family per experiment, one agent product, one model family;
  - Haiku for the probe;
  - Camel is likely in the training data;
  - the probe's 100k window.

  Samples are small throughout, and the authors claim direction only.

**Mine.**
1. **The matrix's pull-vs-push contrast is weak.** It is V1 (n = 1) against H1 and H2 (n = 2): independent runs, not
   paired from a shared state. Wall-time spreads of 2.4-4.4x within arms swamp any 10-20% difference.
2. **"Same content" holds only at the store.** All three seeded arms held the same four notes, but what entered
   context differed:
   - H's index carried three of the four;
   - CS injected 5 times;
   - V saw nothing unless it queried, and it never did.
3. **"Use" is weakly evidenced.** The evidence is calls to the memory tools themselves (H1's first three calls recall
   the injected ids), plus turn and cost counts. Nothing shows that the delivered content changed where the agent read
   or what it edited. Nothing controls for the note content being discoverable anyway, and the agent did recover the
   dropped note's content from code.
4. **"Injection begets engagement" is a cross-experiment comparison.** It sets M (Haiku 4.5, audit workload) against
   V (Sonnet 5, feature task).
5. **One sentence overstates.** The consistency sentence in §5.4 is contradicted by the paper's own numbers (see
   Results). There is also a small rounding slip: -29.4% is printed as -30%.
6. **The false-alarm bound is loose.** Zero false alarms in 35-40 evaluations per run only bounds the rate below
   about 8% per run (about 4% pooled).
7. **No test with wrong memories.** Stale-memory poisoning is named as a design constraint, and a sleeper-attack
   benchmark is cited, but neither is tested.
8. **The decay probe does not speak to pull vs push.** It compares conversation-held facts (N) with injected facts
   (M), and N has no voluntary memory tools.
9. **A motivating citation is stretched.** The paper says MEMTRACK shows "systematic failure" to use memory; MEMTRACK's
   own abstract says "challenges" (best model 60% Correctness). TriggerBench is characterized accurately (abstract
   level).

## Assumptions the paper does not test

- **That delivered memories are acted on,** rather than merely present. The "verify" provenance frame could lower
  trust in them; this is not measured.
- **That injection is safe when the memory is wrong.** The staleness check fires only when the anchored file has
  changed since the note was written.
- **That results transfer** to small or open models, other repositories, issue repair, or a hard context cap without
  compaction.
- **That the symbol (code-graph) trigger works.** It never fired.
- **That the zero voluntary use is not an artifact** of the guidance wording or the tool names.

## Overlap with the idea, component by component

**C1 Setting: partly.**
- It is a coding agent (Claude Code) on a real feature task, with a code-indexing daemon and semantic-search tools.
- But the models are frontier and closed (Sonnet 5, Haiku 4.5), the window is about 200k with compaction rather than
  a hard small cap, the task is a feature rather than issue repair, and there is only one task.
- The code-symbol-graph trigger was implemented but never fired (§7).

**C2 Delivery: partly.** Of the two papers, this one is closer on the delivery manipulation itself, but it delivers
memory notes, not graph relations.
- **What is pushed:**
  - H: a compact index of the seeded notes, injected by the prompt-submit hook at launch (3 of the 4 notes; the index
    budget dropped one); a path-triggered gotcha delivered in full on the first touch of its anchored file; and
    re-injection at compact-resume.
  - CS: API-proxy injection (5 injections in 241 decisions).
  - M (probe): ten one-line facts at every compact-resume, about 240 tokens each.
- **What is pulled:**
  - V: the same four notes in the store, the same MCP memory tools (recall by id, semantic recall, remember, forget)
    and the same guidance, with the hooks removed.
  - B: the same, with a cold store.
- **Is the content the same?** At the store level, yes: the same four seeds in CS, H and V. At the level of what was
  visible, no: H's index carried three of the four, CS injected 5 times, and V saw nothing because it never queried.
- **Presentation:**
  - Index tier (title line now, expand on demand) vs full content. The probe's preflight found that only the index
    line travels at session boundaries, so a fact has to sit in that line itself (§5.7, last paragraph).
  - During the probe, the prompt-submit index tier delivered only 3/10 and then 1/10 of the fact tokens.
  - This is the closest analog to the idea's bare names vs names + signature + file:line: what is written in the
    visible line is what arrives.
- **Budgets:**
  - the index budget is not given as a number;
  - about 240 tokens per probe delivery, about 34k across 139 deliveries;
  - a matrix context of about 190-200k (implied by §5.5);
  - in the probe, compaction at 100k and a read cap of 8k or 6k.
- **Models:** Claude Sonnet 5 (matrix), Claude Haiku 4.5 (probe).
- **Effect sizes:**
  - Uptake: 0 voluntary calls in 114 turns (V), vs expanding all three injected ids within seconds (H1) or one recall
    at about 17 s (H2).
  - Turns: 95 and 102 (H) vs 114 (V).
  - Cost: $5.22 and $6.09 vs $6.23.
  - Wall: 1454 and 1187 s vs 1297 s.

  This is n = 2 vs 1, independent runs, with no uncertainty. The authors call it directional and estimate that 15-20
  runs per arm would be needed.

**C3 Truth: not covered.**
- No wrong note is planted.
- What it has instead:
  - staleness warnings when an anchored file changed after its note was written, after which the agent superseded the
    obsolete gotcha (§5.2, §5.6);
  - a "verify" provenance frame on injected content (§3).
- Stale-memory poisoning is named as a design constraint, citing a sleeper-attack benchmark, but is not tested.
- Adjacent observation: continuation summaries carried a confabulated task state forward across boundaries (§5.7).

**C4 Method: not covered.**
- Runs are independent (n = 1-3 per arm; one run per decay arm), with no saved-state forks.
- Its provenance forensics is worth borrowing: deciding from audit logs whether a fact in the output came from
  injection or from the agent digging through session files. We could use the same approach to attribute a read to the
  delivered graph rather than to independent search.

**C5 Claim: partly.**
- The first half (visible beats queryable) is the paper's thesis, shown for memory notes, with frontier models and
  n = 1-3.
- The second half is only partly present:
  - against it, the paper treats voluntary memory-tool calls after injection as engagement, which is tool calls used
    as evidence;
  - for it, it gates its claims on audit logs rather than on agent compliance, and it records a summary that claimed
    all ten facts were maintained while carrying none (pilot, k = 2): a stated belief contradicted by the record.
- It also shows that pushing begets pulling: the agent queried the store only after content was injected. In our
  design, then, tool calls after a push are downstream of visibility, not independent evidence of use.

**C6 Cross-domain: not covered.**

## What it does NOT do that the idea needs

1. Use code-graph content. It delivers memory notes, and its symbol (graph) trigger never fired.
2. Fix the visible content across delivery arms, and measure where the agent reads or edits next. It measures
   availability, memory-tool calls, turns and cost.
3. Plant wrong content and score following against a base rate.
4. Run paired forks from a saved state. It has 1-3 independent runs per arm.
5. Use a small open model under a hard context cap. It uses Sonnet 5 and Haiku 4.5, with about 200k windows and
   compaction.
6. Cover many tasks, or issue repair at all. It has one feature task in one repo, plus one audit workload.
7. Run any statistics.
8. Anything outside coding agents (C6).

**Useful for us anyway:**
- It is the clearest prior statement of C5's first half for coding agents. Cite it, and differentiate on graph
  content, content fixed at the visible level, forks, and truth manipulation.
- Put the actionable part (file:line) on the visible line, because index-only delivery drops what sits behind the
  expand step.
- Log exactly what was pushed on each turn, because transcripts may not record hook payloads.
- Pushing has a context cost that a tight window feels first. M needed a smaller read cap and cost 21% more turns.
