# Counterfactual Rollout Replay: Forkable Environments as Free Process Rewards for Software Engineering Agents

- **arXiv:** 2609.33875 (v3, 03 Oct 2026, cs.SE, CC BY 4.0)
- **Authors:** Yuanhao Li, Hongbo Wang (corresponding), Xuhong Chen, Yiming Cao, Xunzhu Tang (State Key Laboratory of Networking and
  Switching Technology, BUPT; University of Luxembourg)
- **Read:** 2026-10-27, from the HTML full text (`lit.py fulltext`) plus the 35-page PDF for every figure and table.

**Verdict on overlap.** This is the closest prior work on the *mechanics* of C4: it snapshots and restores an SWE agent
mid-trajectory, forks at selected steps, and rolls the fork forward. But it always forks the **action**, never the
**content of an observation**. It scores forks only by terminal or working-tree verifier return, and it uses that score as
a training credit signal, not as a behavioural measurement. C1 is partly covered (an open 14B model on end-to-end SWE
repair, but no graph tools, no context limit and no quantization). C2, C3, C5 and C6 are not covered.

## Claim

- **Main result (Table 2).** At up to k=4 selected steps per trajectory, CRR replaces GRPO's outcome advantage with an
  executed return contrast, Â_t = R(τ) − R(τ̃_t). For Qwen3-14B this raises pass@1:

  | Benchmark | GRPO | CRR |
  |---|---|---|
  | SWE-bench Verified | 36.4 ± 0.8 | 41.7 ± 0.6 |
  | SWE-bench Live | 31.1 | 35.9 |
  | SWE-rebench | 27.9 | 32.6 |

- **Equal wall-clock comparison (Sec 5.3, Table 15, Fig 2 right).** On the same 8×H100 node at 40.125 h, CRR reaches 41.7
  against 36.7 for extended GRPO (+5.0), with all fork overhead charged.
- **Mechanism (Tables 3 and 17).** The same forks work better for credit assignment than for picking a better training
  sequence. At 48 H100-h per arm over 3 seeds: CRR 36.2 ± 0.6, Search-Select 34.4 ± 0.8, GRPO 33.3 ± 0.7. CRR is higher
  in all three paired seeds, by 1.8 points on average.
- **Theory.**
  - Prop 1: for a *fixed* index, E[Â_t | h_t⁺] = Q(s_t, a_t) − E_{ã∼q¬a}[Q(s_t, ã)]. This is an action-conditional
    contrast for the stated proposal, not the classical advantage.
  - Prop 2: a variance decomposition with a sufficient covariance condition. The authors say explicitly that it is not a
    universal variance-reduction result.
  - The implemented selector induces a selector-weighted objective with no convergence guarantee (Sec 4.1).

## Method (enough to reproduce)

- **MDP (Sec 3).**
  - State s_t = repository working tree + issue + conversation history + tool observations.
  - Action = one JSON tool call per turn.
  - R(τ) ∈ {0,1}: the final patch passes the held-out tests.
  - Horizon H = 50 turns.
  - Transitions are assumed deterministic for admitted tasks.
- **Forkability (Sec 3).** A snapshot σ and restore ρ such that any fixed action sequence run from ρ(σ(s_t)) has the same
  trajectory distribution as when run from s_t.
- **Per training iteration (Algorithm 1, App B).**
  1. Sample G=8 on-policy trajectories per task.
  2. Score every non-terminal step: score(t) = H_t · (1 + λ_type · type(a_t)).
     - H_t is the mean grammar-masked next-token entropy over the semantic tokens of the emitted tool call.
     - type is 0 for read/search, 0.25 for a focused test, 0.75 for shell, and 1.0 for an edit. Submit is excluded.
  3. Keep the top k=4 steps with H_t > η (η = 0.4, λ_type = 0.6). Skip a step when the policy is near-deterministic there
     (Sec 3, 4.3, Table 7).
  4. For each selected t:
     - snapshot σ(s_t);
     - sample ã_t from q¬a_t(a | s_t) ∝ π(a | s_t)^{1/T_cf} · 1[a ≠ a_t], with T_cf = 0.7, rejection-conditioned to differ
       from a_t (Sec 4.4);
     - restore, then roll forward on-policy until submit or the 50-turn cap;
     - record R(τ̃_t). One counterfactual per selected step (K = 1).
- **Hybrid advantage (Eq 3).**
  - Selected steps get R(τ) − R(τ̃_t).
  - All other steps get R(τ) minus the mean of the 8 sibling returns.
  - This goes into the PPO-clipped surrogate with a KL penalty (Eq 4).
  - The realised trajectory is always the one trained on. Branches are never substituted for it.
- **Training (Table 7, App O).**
  - Qwen3-14B with LoRA, rank 128 / alpha 256.
  - AdamW (β = 0.9, 0.95), learning rate 5e-6, 100 warmup steps, 4,000 updates.
  - KL β = 0.04, clip 0.2, γ = 1.
  - 24,000 on-policy trajectories (256 per collection, about 94 rounds).
  - Seeds {11, 23, 47} set policy init, the group sampler and the counterfactual proposal.
- **Infrastructure (Sec 4.5, 5.1).** SkyRL-Agent asynchronous rollouts and SWE-MiniSandbox execution on one 8×H100 node.
  Fork workers are logical roles whose device-time is charged to that node.
- **Tools (App E).**
  - `view_file(path, start, end)` returns up to 200 numbered lines.
  - `edit_file(path, start, end, replacement)` returns a diff.
  - `run_shell(command, timeout)` has a 60 s default timeout.
  - `run_tests(test_filter)` and `submit_patch()`.
  - stdout is truncated deterministically. Decoding is constrained by a JSON grammar. The system prompt is printed in
    App E.
- **Determinism controls (App F).**
  - A three-rerun consistency filter runs the canonical patch three times (different seeds, shuffled test order). It drops
    6.8% of SWE-Gym and 9.4% of SWE-rebench candidates. Per-repo rates are in Table 8: requests 18.8%, flask 12.3%,
    django 11.7%, sympy 4.1%.
  - A frozen package mirror.
  - An HTTP replay layer that records request/response pairs and matches them on method, URL and a normalised body
    digest. A mismatch excludes the task.
  - What survives the filters: filesystem iteration order in glob-heavy tests.
- **Data (Sec 5.1, App F).**
  - 3,638 admitted training tasks: 2,438 SWE-Gym + 1,200 SWE-rebench.
  - The SWE-rebench train/eval split is made by collection month before filtering, then de-duplicated by task id, issue
    and PR URL, commit window, and exact or near-duplicate patch and issue text.

### Fork mechanics (the C4 questions)

- **What is saved.**
  - Algorithm 1 line 6 snapshots σ(s_t), and s_t is defined to include the working tree, issue, conversation history and
    tool observations (Sec 3). So the fork restores both the messages and the sandbox.
  - The paper never says *how* the snapshot is made physically: nothing on filesystem snapshots, copy-on-write, process
    images or KV cache.
  - I looked up SWE-MiniSandbox (arXiv 2602.11210, abstract only). It describes kernel-level isolated workspaces and
    environment pre-caching, and says nothing about mid-episode snapshot/restore.
- **RNG.** Not shared between arms. The counterfactual continuation is sampled independently from π, and the paper
  stresses that policy-sampling variance remains even with deterministic transitions (Sec 1, Sec 3, App A). Seeds are
  run-level only (App O). The contrast is *realised run vs one fork*, not *fork vs fork*.
- **Replay.**
  - The prefix is restored, not re-executed.
  - Network effects come from recordings (the HTTP replay layer), and installs hit the frozen mirror (App F).
  - "Replay" in the title means restore plus a new rollout.
- **Sampling settings (App E).**
  - Training rollouts: T = 0.6.
  - The forked first action: T_cf = 0.7, excluding a_t.
  - The rest of the fork is described as on-policy. I read that as T = 0.6; the paper does not state it separately.
  - Evaluation: greedy (T = 0), plus T = 0.6 for the 8-sample evaluation.
- **What is measured after the fork.**
  - Only R(τ̃_t) ∈ {0,1}, from the held-out tests at submit or the 50-turn cap.
  - For truncated horizons h ∈ {2, 4, 8}, the verifier is run on the fork's current working tree (Sec 5.5).
  - Logged per fork (App N): task id, policy version, index t, snapshot id, a_t, ã_t, both action suffixes, both returns,
    proposal log-prob and selector score.
  - **Nothing about where the agent reads or edits next in the fork is measured.** The only location-type statistic is
    Table 23's "hits gold-patch file on first touch", and it scores the selected *realised* step in order to evaluate the
    selector.
- **Does it ever vary the content of an observation?** Not as a treatment. The fork always changes the action
  (ã_t ≠ a_t). The single place observation content is altered is the replay-noise robustness test (App P.7, Table 20):
  - a fraction ρ ∈ {5%, 10%} of replayed steps gets an output resampled from the recorded rerun distribution, so the
    substitutes are natural rerun outputs, not planted content;
  - the effect is read only from the trained policy's final pass@1 (36.2, then 35.6, then 34.8) and a mean advantage shift
    of 0.01–0.02;
  - there is no measurement of behaviour at the perturbed step.
- **Cost.**
  - A full run costs 321 H100-h per seed: 164 for rollout, 133 for the fork pool and 24 for the learner (Table 14).
  - About 96,000 counterfactual tuples per seed (Table 13), and about 1.4M across all runs (App N).
  - Per 64-trajectory dispatch microbatch (Table 12), CRR adds fork/materialisation 36.2 s, counterfactual rollout 28.1 s
    and counterfactual tests 6.3 s: 170.9 s against GRPO's 100.1 s (1.71×).
  - Fork-slot utilisation was 78%, and 58% of fork time overlapped generation (App P.1).
  - The gain over GRPO disappears as the fork cost multiplier m grows: +2.8 at m=1, +1.4 at m=2, −0.2 at m=4 (Table 16,
    one seed).
- **Short continuations still carry signal.** With h = 2 turns before the working-tree verifier, pass@1 is 39.4, against
  41.7 at full horizon and 36.4 for GRPO. That is about 57% of the gain (Fig 3c, my reading of the plot and my
  arithmetic). h = 4 gives 40.5 and h = 8 gives 41.2.

## Setting, data and models

- **Policy.** Qwen3-14B with LoRA. No quantization is stated, and no context window is stated anywhere (I searched the
  full text). 50-turn cap.
- **Train / evaluate.**
  - Train on SWE-Gym + SWE-rebench (Python).
  - Evaluate on SWE-bench Verified (500 instances), SWE-bench Live and held-out SWE-rebench Python.
  - Greedy pass@1, 3 seeds (Sec 5.1).
- **Baselines (Table 2).** All reproduced on the same backbone and scaffold: SWE-agent and OpenHands zero-shot, SWE-Gym
  SFT, SWE-Fixer, RLEF, Murphy, SkyRL-Agent GRPO, SWE-Trace (rubric PRM), and TSR+GRPO.

## Metrics (exact definitions)

- **pass@1.** Greedy decoding with the 50-turn cap; the fraction of instances whose final patch passes the held-out
  tests; mean ± SD over 3 training seeds (Sec 5.1).
- **Sampled pass@k and all-8.** 8 completions per instance at T = 0.6. all-8 is the fraction of instances solved by all 8
  samples, a consistency measure (Tables 5 and 18).
- **Advantage SNR.** |Â*_t| relative to its SD across the rollout pool, logged every 200 updates. It is an advantage
  diagnostic, not the gradient variance (App C).
- **Bucket covariance (App C, Table 6).** Within-bucket Cov(R(τ), R(τ̃_t)), averaged across buckets weighted by size.
  Buckets are task id × selected-step decile × a prefix signature (the first ten semantic tokens of the realised action
  history).
- **Device-time.** Scheduler-attributed H100-hours per role (Table 14).
- **Error modes (App I).** A deterministic post-hoc classifier assigns each failure to wrong localisation, partial fix,
  regression, harness subversion or other. The taxonomy is from Wang and Ammanabrolu 2025.

## Results, including weak and negative ones

- **Main (Table 2).** CRR 41.7 / 35.9 / 32.6 against GRPO 36.4 / 31.1 / 27.9 and SWE-Trace 39.1 / 33.7 / 30.2 on
  Verified / Live / rebench. These runs are **not compute-matched**: 321 vs 188 vs 233 H100-h (Table 1).
- **Composition (Table 4).** Adding CRR raises none / TSR / PRM / TSR+PRM by 5.3, 5.6, 5.8 and 5.6 points; the best is
  45.6. No seed SDs are shown.
- **Multi-sample (Table 18).** pass@8 is 57.7 vs 53.8; all-8 is 23.9 vs 18.7.
- **PPO outer loop (App G).** CRR-PPO 41.4 ± 0.7 against outcome-only PPO 34.1 ± 1.0. Table 2's "RLEF (outcome-only PPO)"
  row is 33.5 ± 1.0; the paper does not reconcile the two outcome-only PPO numbers.
- **Weak and negative results:**
  - **The selector does most of the work.** Fig 3b, my reading: random-k 37.2 (only about +0.8 over GRPO), stride 38.5,
    tool-type only 39.4, entropy only 40.6, entropy + tool type 41.7.
  - **The fork budget saturates (Fig 3a).** k = 0→1 gains 2.2. k = 4 gets 5.3 of the 5.6-point gain seen at k = 16, at
    about 1.7× relative wall-clock against about 4×.
  - **Temperature (Fig 3d, my reading).** Flat at 41.5–41.7 for T_cf between 0.6 and 1.0, but 39.2 at 0.2 and 38.9 at
    1.4. The zero-contrast control plotted at 0 equals GRPO (36.4).
  - **More counterfactuals per step barely help (App G).** K = 2 adds 0.4 at 1.6× counterfactual cost; K = 4 adds 0.6 at
    3.2×. At a matched fork count, spreading forks over more steps does at least as well (Table 19, one seed: 36.2 vs
    35.8 vs 35.0).
  - **Replay noise hurts (Table 20).** 36.2 → 35.6 → 34.8 at ρ = 0 / 5 / 10%. K = 2 recovers 0.4–0.6.
  - **Fork overhead (Table 16).** The margin over GRPO is +2.8, +1.4 and −0.2 at m = 1, 2, 4.
  - **Fork quality (Table 21, 20,000 logged forks).**
    - 12% immediately invalid alternatives (mean contrast +0.15).
    - 46% valid alternatives whose branch fails (+0.40).
    - 42% valid alternatives whose branch succeeds (−0.05). So in roughly two forks in five, the alternative action does
      not change the outcome.
    - A validity filter moves pass@1 from 36.2 to 36.4 (Table 22): no evidence the gain needs invalid alternatives.
  - **Error modes (Tables 10–11).**
    - CRR cuts partial-fix failures (absolute 25.25 → 14.11) and regressions (12.34 → 6.59).
    - **Wrong-localisation failures rise slightly**: absolute 21.75 → 23.03, and from 34.2% to 39.5% of failures.
    - A new "Other" bucket appears (10.73 absolute) that the classifier cannot assign.
    - Harness subversion persists (6.6% of CRR failures).
    - Wrong localisation is the dominant mode on deep-abstraction repos such as sympy and astropy (App I).
  - **Interface errors.** The grammar decoder rejects 1.4% of tokens early in training and 0.3% at convergence (App G).
  - **Curriculum.** Sorting tasks easy → hard helps GRPO by +0.7 and CRR by +0.2 (App G).

## Limitations

**The authors' (Sec 6, App M):**

- It needs cheap, reliable forks and a trustworthy verifier, and expensive restoration erases the gain.
- Trajectory-length skew is not isolated.
- Averaging does not remove systematic replay bias.
- Unbiasedness holds only for a fixed index; the selector-weighted objective has no convergence guarantee.
- The selector diagnostics are proxies, not per-step causality.
- Binary rewards are assumed.

**Mine:**

- **Compute matching.** Only the comparisons against vanilla GRPO are compute-matched: Table 15, plus the 48 H100-h
  controls, most of which are single-seed. The endpoint table is not.
- **Statistics.** No significance tests; 3 seeds; most sensitivity sweeps use one seed.
- **Tuning on the test set.** The Fig 3 ablations and the validity-filter check are reported on Verified, which is the
  test set. The tuning account is ambiguous:
  - App D says the CRR parameters were not tuned separately from GRPO.
  - The checklist says they came from a single sweep on a held-out 200-instance SWE-Gym subset.
- **Fig 2 left vs Table 15 and Tables 16–17.** The mismatch above weakens the trajectory-efficiency claim.
- **No release.** Code and the counterfactual dataset are not released in this version (checklist item 5).
- **Unrelated citations.** App M cites a lot of work unrelated to the method (UAV hovering control, A* grid navigation,
  short-video moderation, remote-sensing video QA). It carries no evidence.

## Assumptions the paper does not test

- **That the restored state behaves like the original.** Determinism is checked only for the canonical patch's tests
  (App F). Nobody checks that a restored agent, given the realised action, reproduces the realised continuation
  distribution.
- **That the contrast comes from information entering context.** App J case 1 has a fork that reads documentation instead
  of the test file and then fails, which hints that what is in context matters. But it is one sampled pair, the
  treatment is still the action, and the authors say a single pair does not establish causality.
- **That entropy-selected steps are where localisation is decided.** Wrong-localisation failures did not fall
  (Tables 10–11).
- **Other models and settings.** One 14B model only. No context-budget stress. No quantized model. No other tool
  catalogue.

## What it does NOT do that the idea needs

1. **Vary the content of an observation at the fork** (graph pulled by tools vs pushed into context; true vs decoy edge).
   CRR's treatment is always the action.
2. **Pair arms on a shared seed.** CRR samples continuations independently and contrasts the realised run with one fork.
   The idea needs fork-vs-fork arms that differ only in delivery or truth.
3. **Measure behaviour right after the fork**: which file or function is read or edited next, and whether the agent goes
   to a decoy target. CRR scores verifier return only.
4. **A base rate for "following"**: visits to the same target when the graph is true.
5. **Code-graph tools, a hard context budget, a 4-bit model, or graph presentation variants** (bare names vs signature +
   file:line).
6. **Inference-time measurement.** CRR is a training method, and its fork is a credit estimator.

**Worth borrowing:**

- the forkability definition (Sec 3);
- the determinism controls: three-rerun filter, package mirror, HTTP replay (App F);
- the entropy + tool-type step selector for choosing fork points (Sec 4.3). Its steps first-touch the gold-patch file 41%
  of the time against 13% for random (Table 23);
- the evidence that h=2 continuations keep about 57% of the signal (Fig 3c);
- the cost-ledger format (Tables 12, 14, 15).
