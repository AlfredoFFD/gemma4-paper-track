**One-line verdict:** a careful, pre-registered study of what context lets a model make the edit once the location is known. For us it is mostly a boundary condition, not overlap.
- **H2 null.** With localization fixed by an oracle, single-shot Claude Sonnet 4.6 resolves no more multi-file SWE-bench Verified issues when the rest of each file is shown as UML skeletons and signatures (23/70) than when it is deleted (25/70). Discordant pairs 4 vs 6, exact McNemar p = 0.754 (Tables 3-4).
- **Summaries carry little.** NL summaries answer 4/45 behavioral probes vs 27/45 for source (Table 2).
- **Noise floor.** Byte-identical T = 0 re-runs flip 6/70 outcomes, about 9% (§5).
- **What it never studies:** navigation, tools, graphs, pull vs push, wrong information.
- **Coverage of our idea:**
  - C1 partly
  - C2 partly: presentation only, all pushed
  - C4 partly: paired by instance, plus a measured noise floor
  - C3, C5 and C6 not covered

## Claim

- **The act signal is in the edited code itself** (§4, Table 2, Fig. 1).
  - Source answers 27/45 test-minted behavioral probes.
  - Prose summaries answer 4/45, whether written by Claude Sonnet 4.6 or by Qwen2.5-Coder-3B.
  - Signature + docstring answers 6/45.
  - Against source, the discordant pairs are 23 vs 0 for summaries and 21 vs 0 for signatures; all p < 1e-4.
- **Surrounding structure adds nothing at oracle localization, single shot** (§5, Tables 3-4, Fig. 4). Registered H2 (tier > keep/drop) is null, p = 0.754, and keep/drop is nominally ahead.
- **Compression costs nothing** (Table 3). Compressed context resolves at least as well as whole files with 3-3.7× fewer tokens: 19,300 vs 93,700 context tokens per resolved issue.
- **T = 0 API inference is not deterministic.** About 9% of per-instance outcomes flip between byte-identical runs, a floor under small effects on this benchmark (§5).
- **Framing** (§7): one more controlled data point for "the bitter lesson in code context". The lasting contributions are the audited rig and publishing pre-registered nulls.

## Method (enough to reproduce)

1. **Resolve pool** (§3.1 Table 1, §5, Fig. 3).
   - All 71 SWE-bench Verified instances whose gold patch touches ≥ 2 files.
   - astropy-8707 is excluded because its gold patch fails its own environment, leaving 70.
   - Nothing is sampled.
2. **Oracle localization** (§3.2). Every arm gets the gold-changed files, which removes the find step.
3. **Arms.** All are deterministic, built from Python `ast`, with no LLM involved.
   - **Structural tree:** Subsystem → Component → File → Class → Function.
   - **Available rungs:** full-body · method-only · UML-class-skeleton · signature+doc · name · exclude (§3.1).
   - **The three arms:**
     - **oracle_full:** whole gold-changed files, with no highlighting.
     - **oracle_tier:** gold-edited units in full, and the rest of each file rendered as UML class skeletons and signatures (static name/signature digests; §5 Finding 1).
       - §1 describes this as "UML-skeleton / method-only".
       - The rule that assigns a rung to each unit, and an example rendering, are not given.
     - **oracle_keep_drop:** gold-edited units in full, and the rest deleted (binary keep/drop, after SWEzze).
   - **Coverage-fair.** Both compressed arms also render module-level code, class-attribute regions, decorators and non-Python gold files verbatim (§3.2).
   - **Expressibility gate** (Table 1). Before any model call, for every arm × instance, every gold hunk's deleted lines (or insertion anchor) were verified to appear verbatim in the rendered context: 70/70 in all arms.
   - **Disclosed asymmetry.** The compressed arms are built from gold-edited units, so they also tell the model where to edit; oracle_full does not. Tier vs keep/drop shares the same units and is the clean comparison (§3.2, §6).
4. **Interaction-level follow-up, pre-registered H3** (§5). Keep/drop's byte-identical content, plus a deterministic AST-derived "sequence slice" of the gold functions' local call flow.
   - The slice exists on 65/70 instances, with a mean of 215 tokens.
   - Both arms (slice and keep/drop) were run fresh.
5. **Noise measurement** (§5, App. C). The fresh keep/drop run in the H3 follow-up doubles as a byte-identical re-run of the original keep/drop arm: same model alias, same prompts, T = 0.
6. **Model call** (Table 1, App. A).
   - Claude Sonnet 4.6, alias `claude-sonnet-4-6`, with no dated snapshot and no seed (App. B).
   - Single-shot, temperature 0, max_tokens 8,000. Reasoning is allowed before the edit blocks.
   - The prompt is byte-identical across arms except for `{context}`. It contains the repo name, the issue, a "RELEVANT CODE (already localized for you)" block, and strict SEARCH/REPLACE format rules.
   - Up to 2 retry rounds feed back per-edit failures: not found, ambiguous, no such file.
7. **Patches** (§3.2).
   - SEARCH/REPLACE blocks are turned into a difflib unified diff and verified with `git apply --check`, with a uniqueness check. An empty SEARCH creates a new file.
   - In development, model-written unified diffs failed to apply in 7 of 9 attempts. That is why this builder exists.
8. **Scoring:** SWE-bench 4.1.0 Docker harness; resolved = FAIL_TO_PASS ∧ PASS_TO_PASS. Every gold patch is validated first (70/71).
9. **Cost:** cl100k_base token proxy, plus Anthropic `count_tokens` on each episode's initial prompt. Retry prompts are logged but not counted.
10. **Statistics:** Wilson 95% CIs on every proportion; exact two-sided McNemar on paired resolve outcomes.
11. **Probe study** (§4, Table 2).
    - **Data:** 15 held-out classes from seaborn, pylint and pytest at pinned commits, each with a dedicated test file.
    - **Probes:** 3 per class, minted from the tests (n = 45). The answerer never sees them, and "UNKNOWN" is allowed.
    - **Answerer:** Claude Sonnet 4.6 in every arm.
    - **Representations:**

      | Representation | Mean tokens |
      |---|---|
      | full source | 1,124 |
      | summary written by Sonnet 4.6 | 165 |
      | summary written by Qwen2.5-Coder-3B | 180 |
      | signature + docstring | 212 |

      Both summarizers get the same prompt and a 180-token budget.
    - **Judge:** GPT-4o-mini (a different model family), with Claude as a second judge for agreement only.
    - **Clustering:** class-clustered bootstrap intervals in §6.
12. **Exploratory work** (App. D; the paper's own code; no claims made):
    - a pilot probe protocol
    - an act-view ladder
    - hierarchical descent vs flat retrieval

## Setting, data, models

- **Task:** end-to-end issue repair, scored by the real tests, on the multi-file subset of SWE-bench Verified (70 instances).
- **Not an agent loop.** One completion plus apply-failure retries. No tools, no file reading, no navigation, no execution, no test feedback (§6 "Single-shot, no-execution regime").
- **Models:**
  - Claude Sonnet 4.6: resolver, probe answerer, frontier summarizer, second judge
  - GPT-4o-mini: judge
  - Qwen2.5-Coder-3B: summarizer only; it never edits or answers
- **Context sizes:** mean tokens of 25,426 (full), 8,629 (tier) and 6,876 (keep/drop) in cl100k. In Anthropic counts, the mean full prompt is 32.6K, 11.6K and 9.4K (§6). There is no hard cap.
- **Compute** (App. B):
  - about 210 resolve calls (about $20) and about 6 hours of Docker evaluation on a 32-thread workstation
  - about 600 probe calls (about $5)
  - no GPUs

## Metric (exact definitions)

- **Resolved:** the SWE-bench harness passes both FAIL_TO_PASS and PASS_TO_PASS tests.
- **resolve@cost:** the pair (resolve rate, mean context tokens), summarized as tokens per resolve = total context tokens / instances resolved (§3.2). The authors refuse to divide resolve rate by mean tokens, because that ratio rewards shrinking context on instances an arm never solves.
- **Probe accuracy:** the share of the 45 probes that the GPT-4o-mini judge grades correct. Judge agreement is κ = 0.84 (94% raw).
- **Run-to-run flip rate:** the symmetric difference between two byte-identical runs of one arm, divided by 70.

## Results (including weak and negative)

**Probes** (Table 2, n = 45; Wilson 95% CIs):

| Representation | Accuracy | Wilson 95% CI | Tokens |
|---|---|---|---|
| full source | 0.600 (27/45) | [0.45, 0.73] | 1,124 |
| summary, Sonnet 4.6 | 0.089 (4/45) | [0.04, 0.21] | 165 |
| summary, Qwen2.5-Coder-3B | 0.089 (4/45) | [0.04, 0.21] | 180 |
| signature + docstring | 0.133 (6/45) | [0.06, 0.26] | 212 |

- **McNemar vs source:** 23 vs 0 for each summary arm, 21 vs 0 for signatures; all p < 1e-4.
- **Clustered by class** (§6): source [0.40, 0.78] vs summaries [0.00, 0.20], gap CI [0.36, 0.67].
- **Signatures vs summaries,** 6/45 vs 4/45: the paper itself calls this "no more than a hint".

**Paired tests** (Table 4, exact two-sided McNemar; A-only / B-only / p):

| Comparison (A vs B) | A-only | B-only | p |
|---|---|---|---|

- **keep/drop vs full is marginal,** and the authors do not claim it. It also mixes compression with location hints (§6).
- **H3** (§5): slice 26/70 (0.371 [0.27, 0.49]) vs the fresh keep/drop run 23/70 (0.329 [0.23, 0.44]); McNemar 4 vs 1, p = 0.375. This is the only structured artifact that pointed the right way, and it is not significant.
- **Noise** (§5): the fresh keep/drop run resolved 23/70 vs 25/70 originally, with a symmetric difference of 6 instances.
  - 6/70 = 8.6%, Wilson [0.04, 0.175] (my calculation).
  - From 25 → 23 with 6 flips, the split must be 4 lost and 2 gained (my derivation). McNemar on that split gives p = 0.69.
  - So same-arm noise gives 6 discordant pairs, against 10 for H2.
- **Format failures** (§5 Finding 3, §6):
  - 0-1 truncated generations and 1-2 empty patches per arm.
  - The retry loop fired on 24/70 instances for tier, 15 for keep/drop and 11 for full.
  - Tier's synthesized text tempts the model to copy non-verbatim lines.
- **Exploratory** (App. D; the paper's own code; no claims):
  - **(a) Circular pilot:** probes minted from the scored source, answered and graded by the same model; source 15/15, summaries 0/15. The honest protocol drops source to 0.600.
  - **(b) Act-view ladder** (n = 18), with positives partly guaranteed by construction:

    | Rendering | Score | Tokens |
    |---|---|---|
    | full class | 1.00 | 18,661 |
    | UML skeleton + body | 1.00 | 2,814 |
    | method body alone | 1.00 | 900 |
    | signature only | 0.06 | not given |

  - **(c) Descent vs flat retrieval** (n = 16 queries): flat 0.875 [0.64, 0.97] vs cumulative-summary descent 0.812 [0.57, 0.93]; residual-summary keys 0.562.

**Re-derivation:**
- **Exact match.** All Wilson CIs, all McNemar p-values and tokens per resolve recompute (93,675; 26,262; 19,253). Table 4's discordant counts agree with Table 3's resolve counts.
- **Token ratios** (my calculation): full / tier = 2.95× and full / keep/drop = 3.7×, matching "3-3.7×". Per resolve, the ratio is 4.85×.

**Internal inconsistencies and gaps:**
1. **Probe temperature.** §6 says "probe cells are single draws at T=1". §4 says T = 0 throughout, Table 2 says "strict T=0", and App. C cites "the corrected strict-T=0 rerun". The uncorrected run's numbers are never shown.
2. **"A powered null"** (contribution 2), but there is no power analysis. My calculation and simulation:
   - **Splits needed for p < 0.05:** with 10 discordant pairs, a 9-1 split or more extreme; with 20 pairs, 15-5.
   - **Simulation setup:** 70 paired instances, symmetric noise flips of 4.3% each way (about their 8.6%) plus a true one-way gain Δ. Exact two-sided McNemar at α = 0.05; 6,000 simulations per Δ.
   - **Power by Δ:**

     | Δ (points) | Power |
     |---|---|
     | 5 | 0.11 |
     | 10 | 0.40 |
     | 15 | 0.70 |
     | 20 | 0.89 |

   - So the null rules out only effects of roughly 15-20 points or more.
3. **H3's baseline.** H3 is compared against the lower fresh keep/drop run (23), not the original (25). Against the original, slice leads by 1.
4. **"Ownership scoring"** appears only in §7, as a structure-aware method that failed. It is never described or reported.
5. **Call-edge tension.** §5 says interaction-level artifacts were never implemented because "call-edge extraction this codebase lacks". The H3 follow-up then uses an AST call-flow slice. My reading: the slice is a local call sequence, not cross-file call edges. The paper does not say.
6. **No H1.** The registered hypotheses are H2 and H3.
7. **Fig. 1 is hard to read.** The caption says token sizes appear below each bar, but in the figure they are faint grey text printed over the axis labels. The y-axis label is clipped by the title.
8. **Docker re-runs** (App. B). The first evaluation pass hit Docker Hub rate limits and affected instances were "re-run to completion". It is not said whether model calls were re-issued, which would mean fresh samples given a 9% flip rate.
9. **Probe-run history.** "Every number traces to a raw artifact" sits alongside an earlier, non-strict probe run whose numbers are not reported.

## Limitations

**The author's own** (§6, "which way each cuts"):
- **Single-shot, no-execution regime.** This biases toward a null for tier vs keep/drop, and plausibly against full. A multi-turn agent could recover from compressed context by reading more.
- **Oracle ceilings with asymmetric construction.** Compressed arms encode edit locations; realistic retrieval would lower every arm.
- **Probe scope:** one language and 15 classes.
- **A residual format penalty against tier** (more retries).
- **Measured non-determinism.**
- **Token proxy:** cl100k_base, not the model's own tokenizer.
- **One language (Python), one model family.**
- **Thin tiers.** The tiers tested are the thin end of structured artifacts. Interaction-level and distance-graded tiers were specified but not built (§5).

**Mine:**
1. **The "agent" is one prompted call.** The paper's question is answered for a single-call editor handed the oracle files, not for an agent that reads, searches and decides where to go.
2. **Low power** (see Results, item 2). With about 10 discordant pairs and an 8.6% same-arm flip floor, a 5-10 point true effect would usually be missed. "Powered null" is an overstatement.
3. **Thin noise estimate.** The ~9% floor comes from one re-run of one arm (6/70, CI [0.04, 0.18]). Flip rates for the other arms are not measured.
4. **No pinned snapshot.** A model alias with no dated snapshot or seed limits reproduction of the absolute numbers.
5. **Probes are a proxy for acting.** They are question answering about one class's behavior, not editing, and the temperature is inconsistent across sections.
6. **The tier arm is under-specified.** No rendering example or rung-assignment rule, so the null covers one digest that the paper does not show.
7. **The 7 vs 1 keep/drop-over-full signal is confounded** with being told where to edit (the authors say so). That makes location hints, not compression, a live explanation.
8. **Cost favors tier** (my inference). Only initial-prompt tokens are counted, and tier triggered the most retries (24/70), so its true cost is understated relative to the other arms.

## Assumptions the paper does not test

- **That an oracle cleanly removes "find".** The compressed arms also mark the edited units, so within-file location comes back as a hint.
- **That single-shot nulls carry over to multi-turn agents.** This is flagged as future work: a registered 2-step agent loop (App. C).
- **That structure can matter only through its content.** Whether structure in context changes where an agent looks or edits next is never measured.
- **That probe answering stands in for editing ability.**
- **That the results hold for small models or tight context budgets.** The 3B model only writes summaries.
- **That the T = 0 flips come from the provider.** The cause is not diagnosed.

## Answers to the specific questions

- **The arms and how they are built:** see Method item 3. All arms share the gold-changed files.
  - Full shows the whole files.
  - Tier shows the gold-edited units in full plus UML class skeletons and signatures for the rest.
  - Keep/drop shows the gold-edited units and deletes the rest.
  - The follow-up adds an AST call-flow slice to keep/drop.
  - All are deterministic, from `ast`, with coverage-fair verbatim regions and an expressibility gate.
- **Models:** Claude Sonnet 4.6 for resolving, probe answering, frontier summaries and the second judge; GPT-4o-mini as judge; Qwen2.5-Coder-3B as a summarizer only.
- **How "finding" and "acting" are separated:**
  - **Resolve experiment:** finding is removed by oracle localization (the gold-changed files, and for the compressed arms the gold-edited units), so only acting is scored, by the real tests.
  - **Probe experiment:** act-relevant knowledge is measured as behavioral questions about one class given its representation, with no finding at all.
  - **Navigation proper** appears only in an exploratory own-code test (App. D(c), n = 16).
- **Pre-registration** (§1 "Rigor and scope", §5, App. C):
  - **Frozen and committed before any data:**
    - the sample: all 71 multi-file instances
    - the arms: coverage-fair
    - per-instance gold validation and expressibility instrumentation
    - the statistics: Wilson CIs plus exact McNemar
    - the directional H2 (tier > keep/drop), with a tie to be reported as the result
  - **The probe re-grade was also registered:** held-out classes, test-minted probes, an independent judge with κ, a frontier-summarizer control, T = 0.
  - **H3** (slice > keep/drop) was registered for the follow-up.
  - **Registered as future work:** a 2-step agent loop on the solvable subset, and an act-view re-grade.
  - **Not given in the paper:** commit hashes or dates, α, a power analysis, stopping rules. The registration files are said to ship in the repo, which I did not check.
- **The exact noise-floor measurement:**
  - The H3 follow-up re-ran the keep/drop arm under the byte-identical protocol (same alias, same prompts, T = 0).
  - It resolved 23/70 vs 25/70, with 6 instances differing.
  - 6/70 = 8.6%, reported as "~9%". This is one pair of runs of one arm.
  - The split is necessarily 4 lost and 2 gained (my derivation).
- **What it implies for a presentation arm** (bare names vs names + signature + file:line) **in a navigation-stage experiment:**
  1. **No direct evidence either way.** The nulls are explicitly about rendering context for acting, not navigation (§2). The one navigation test is exploratory.
  2. **Signature text should not help the edit itself.** Signatures carry little act-relevant behavior (6/45 vs 27/45 for source; 21 vs 0). Any benefit from showing signatures must come through navigation, by changing where the agent reads next.
  3. **Do not score the presentation arm on final resolve.** Names + signatures for the remainder did not move resolve rates, and a 2-3 instance difference at N = 70 is inside the 9% flip floor. Score where the agent reads or edits next, at the decision point. They never measure this, so it is open ground.
  4. **The one nominal signal in the paper is location** (keep/drop over full, 7 vs 1, p = 0.07, confounded with telling the model where to edit). A file:line field is a location pointer. My guess: if the presentation arm moves behavior, the pointer is more likely to matter than the signature.
  5. **Expect interface failures from rendered text.** Rendered, non-verbatim structure caused the most edit-apply retries (tier 24/70 vs 15 and 11). A small model shown signatures may copy rendered text into SEARCH blocks; count these as interface failures, separately.
  6. **Report or match tokens.** Tier used about 25% more tokens than keep/drop (8,629 vs 6,876). Names-only vs names + signature + file:line differ in tokens too, which matters under a 16k cap.
  7. **Measure our own noise floor.** Re-run identical forks, as they re-ran an identical arm. Local fixed-seed decoding may still not be bitwise deterministic.

## What it does NOT do that the idea needs

- **No navigation-stage outcome.** It never measures where an agent reads or edits next.
- **No pull vs push.** No tools, no graphs, no tool-call behavior.
- **No wrong information.** No planted decoy edge, no following rate, no base rate.
- **No multi-turn agent and no saved-state forks.**
- **No small quantized model under a hard context cap.**
- **Interface failures only partly counted.** Retries, truncations and empty patches are reported. Edit mismatches are folded into retries rather than classified.

**Useful for us:**
- **A noise-floor recipe.** Re-run an identical arm byte-for-byte and report the flip count; theirs is 6/70 at T = 0 through an API. Our paired forks should do the same at the fork level.
- **An expressibility gate.** Verify, before any model call, that every arm contains what the scored behavior needs. For us: the decoy target and the true target must both be reachable in every arm.
- **A pre-registration style worth matching.** Register the direction and say in advance that a tie is the result. Publish the null with its CI and power.
- **A framing hint.** "Signatures carry little act signal" supports presenting our presentation arm as a navigation manipulation, not an editing aid. Cite this paper as the act-stage null we do not contradict.
