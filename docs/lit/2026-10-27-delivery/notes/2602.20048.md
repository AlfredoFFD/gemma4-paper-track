## Claim

- **Navigation Paradox** (§2, §6.1): bigger context windows move the failure from retrieval capacity to "navigational salience". Agents miss files that are structurally required but lexically unrelated to the task.
- **The graph helps on hidden-dependency tasks** (§5.1, Fig. 7). Mean ACS on G3 is 99.4% (Graph) vs 76.2% (Vanilla) vs 78.2% (BM25).
  - That is +23.2 points over Vanilla and +21.2 over BM25.
  - The body abstract and the Fig. 7 caption say +23.2 over both, which is wrong for BM25.
- **BM25 is best on keyword-findable tasks** (§5.1). G1 ACS is 100% for BM25 vs 90.0% Vanilla vs 88.9% Graph.
- **The bottleneck is adoption, not the graph** (§5.3, Figs. 3-4):
  - 58.0% of Graph-arm trials made zero MCP calls despite an explicit instruction.
  - Trials that called the tool averaged 99.5% ACS; trials that did not averaged 80.2%.
  - By group, adoption was 0/30 on G2 and 31/31 on G3 (after a prompt revision).
- **Prompt engineering raises adoption** (§5.3, §7). A checklist moved to the end of the prompt took G3 adoption from 85.7% (30/35) to 100% (31/31), and G3 ACS from 96.6% to 99.4%.
- **Design advice** (§6.3, §6.6): force the first graph call (tool_choice) or use a planner agent. A curated, human-validated graph is a deployment assumption (§4.2, §6.4).

## Method (enough to reproduce)

1. **Repo** (§4.1). FastAPI RealWorld example app (Nsidnev 2021):
   - a Medium-like blogging API, about 3,500 lines and 40 source files
   - repository pattern with dependency injection
2. **Tasks** (§4.1). 30 hand-written natural-language modification prompts, each with a gold list of files that must be read or edited. The gold lists were checked by manual inspection. Three groups:
   - **G1 Semantic (tasks 01-10):** required files are keyword-findable. Example: change the "incorrect email or password" message; BM25 surfaces `app/resources/strings.py`.
   - **G2 Structural (tasks 11-20):** required files lie 2-4 import hops from the file(s) the task names. Example: "Extract RWAPIKeyHeader to app/api/security.py" also needs `authentication.py`, `routes/api.py` and `main.py`.
   - **G3 Hidden (tasks 21-30):** required files have no lexical overlap with the task and are reachable by graph traversal. Example (task 23): add a logger parameter to `BaseRepository.__init__`, which also needs `app/api/dependencies/database.py`.
   - Appendix A, the full task table, is missing ("to be attached").
3. **Graph** (§4.2).
   - Built with Python's `ast`. Nodes are files: 71 nodes, 255 edges.
   - Edge types: 201 IMPORTS, 20 INHERITS, 34 INSTANTIATES. Relative imports are resolved to repo-relative paths.
   - Stored in Neo4j 5.15 and served by a FastMCP server.
4. **Tools exposed in Condition C** (App. B):
   - `get_architectural_context(file_path)`: the 1-hop neighborhood in both directions. Its docstring tells the agent to use it before editing any file.
   - `semantic_search(query, top_n=8)`: BM25 over function/class chunks, returning ranked files.
5. **Tool output format** (§4.2 textual example). One line per edge: an arrow for direction, the edge type, and a repo-relative file path. For example, `← [IMPORTS] app/api/dependencies/database.py`. The output ends with "Total: N structural connections".
   - No symbol names, no signatures, no line numbers. Files only.
   - Only the inbound arrow appears in the example; the outbound format is not shown.
6. **Conditions** (§4.3 table):
   - **A Vanilla:** raw task prompt; Claude Code built-ins (Glob, Grep, Read, Edit).
   - **B BM25:** the top-10 BM25-ranked files are prepended to the prompt.
     - Query: the task text.
     - BM25 (rank-bm25) runs over 339 function/class chunks, with each file scored by its best chunk.
     - The format of the prepended list is not given.
   - **C Graph:** the MCP server is registered. The task prompt tells the agent to call `get_architectural_context` on the primary task file first, and to read all returned neighbors before editing.
7. **Mid-study prompt revision** (§5.3). Initial G3 trials adopted the tool in 30/35 trials. The author then wrote an improved prompt with a "mandatory checklist" at the end and re-ran G3: 31/31 adopted.
   - The reported G3 Graph arm is the revised-prompt run.
   - The text implies, but never states, that G1 and G2 Graph trials kept the original prompt.
   - Neither prompt's text is given.
8. **Harness** (§4.5):
   - `claude -p` (non-interactive) with `--dangerously-skip-permissions`; the repo is reset to a clean checkout per trial.
   - The `CLAUDECODE` environment variable is unset before each run.
   - Transcripts are read from `~/.claude/projects/<hash>/*.jsonl`, and ACS and FCTC are computed by `harness/calculate_acs.py`.
   - **Not stated:** Claude Code version, temperature, max turns, timeouts, system prompt or CLAUDE.md contents.
9. **Runs** (§5). 30 tasks × 3 conditions × 3 runs = 270 planned; 258 completed; 12 lost to API credit exhaustion.
   - Per condition: A 89, B 81, C 88 trials.
   - Duplicate Condition C result directories from concurrent runners: the most recent one was kept.
10. **Statistics** (§5.4). Welch's t-test on G3 ACS only: C vs A and C vs B.

## Setting, data, models

- **Model:** claude-sonnet-4-5, inside Claude Code, in every trial (§4.3, §6.5). A frontier model with no context cap. The framing invokes 1M-token windows, but no condition puts the codebase in context.
- **Repo:** one small Python web app, not a SWE-bench repo. The graph is file-level. The competition's graphs are symbol-level NetworkX graphs of fastapi/fastapi, rich, requests and httpx (`docs/competition.md` lines 75-82).
- **Tasks:** hand-written edits with gold file lists. They are not GitHub issues, and there are no tests.

## Metric (exact definitions)

- **ACS** (§4.4, App. C): |files_accessed ∩ required_files| / |required_files|, per trial.
  - Files accessed are parsed from `Read`, `Edit` and `Write` file paths, and from `Bash` commands by a regex for `app/` or `tests/` paths. Paths are normalized to repo-relative.
  - Glob and Grep results do not count.
  - It is recall only: reading extra files is never penalized.
- **Completion rate** (§5.2): the share of trials with ACS ≥ 1.0, meaning every gold file was read or edited. It is reported overall only, not per group.
- **FCTC** (§4.4): the number of tool-call steps before the first access of a required file.
- **MCP calls** (§4.4): the count of `get_architectural_context` and `semantic_search` calls per trial. "Adoption" means at least one MCP call, so it lumps the graph tool with the BM25 tool. The split by tool is never reported.
- **Veto Protocol event** (§4.4): Grep or Bash was called and returned no required file, but the graph tool surfaced at least one. Defined, but no count is ever reported.

## Limitations

**The author's own** (§6.5):
- one codebase
- ACS is not correctness
- the result depends on prompt design
- one model (claude-sonnet-4-5)

Also, graph quality is treated as a deployment assumption, and the automated graph as a "lower bound" (§4.2, §6.4).

**Mine:**
1. **The coverage gain is mostly instructed reading.**
   - The graph prompt orders the agent to read every returned neighbor, and ACS rewards reads with no precision penalty. A call that returns 7-10 neighbors, followed by reading them all, raises ACS mechanically.
   - G3 precision and files read are not reported; precision is given for G2 only.
   - So "99.5% when used" mostly measures compliance with "read all neighbors". It is not evidence that the structure guided choices.
2. **G3 is built around the tool.**
   - G3 files are, by definition, near-zero lexical overlap and 1-2 hops from the file the task names. The tool returns exactly 1 hop from a named file.
   - G2 needs 2-4 hops, which one call cannot reach.
   - The author wrote the task taxonomy, the gold lists and the tool, and the task list (App. A) is missing, so none of this can be audited from the paper.
3. **The prompt was revised after seeing the data, for G3 only.** The 99.4% headline is the best prompt, and the 0% vs 100% adoption contrast mixes task groups with prompts. Even so, the original-prompt G3 arm (96.6%) already beats Vanilla by 20.4 points, so the G3 effect does not hinge on the revision.
4. **"Adoption" counts the BM25 tool too.** The conditions table marks C as having no BM25, yet `semantic_search` (BM25, pulled) was available in C. Adoption is never split by tool.
5. **Weak statistics.**
   - There are 3 runs per task with no task-level or clustered analysis.
   - Welch's t is applied to a bounded score with C at its ceiling.
   - No CIs, and no test on completion (my p = 0.10).
   - The arms ran at different times: the G3 Graph arm was re-run after the revision.
6. **The large-context premise is untested.** No arm puts the codebase, or more of it, in context. Every arm reads files through tools. The paradox ("more context does not help") has no "more context" condition.
7. **"Used vs ignored" is confounded with task group** (see Results). The 19.3-point gap is mostly a G3 vs G1/G2 contrast.
8. **FCTC is shaped by the instructions.**
   - In C, the mandated first graph call adds a step.
   - In B, the prepended list removes search.
   - The "graph prioritizes completeness" reading is an interpretation, not a test.
9. **The Veto Protocol is promised but not delivered.** Contribution 5 calls it an empirical metric, but the paper gives one anecdote and no counts.
10. **Weak provenance.**
    - The arXiv comment (SWE-bench-lite) contradicts the body.
    - The listing and body titles and abstracts differ.
    - The references are a stub, and Appendix A is missing.

## Assumptions the paper does not test

- That a tool call means the information was used. ACS counts reads, which the prompt mandates; whether the returned structure changed a decision is never measured.
- That the graph is right. §6.4 says a stale graph could be "worse than no graph" by pointing the agent at wrong dependencies, but no wrong or stale edge is ever tested.
- That the agent skips the tool on G1/G2 because it makes a "rational" cost judgment. No reasoning traces are analyzed.
- That Lost-in-the-Middle explains the checklist-at-END gain. There is one non-concurrent before/after comparison and no position-controlled variant.
- That forcing the call (tool_choice) would fix G2. It is proposed, not run.
- That results transfer beyond one 3,500-line app, one model, and file-level graphs.

## Answers to the specific questions

- **Agent and model:** Claude Code CLI (`claude -p`, permissions skipped) with claude-sonnet-4-5 in all trials. The built-in tools are Glob, Grep, Read and Edit; Write and Bash are also parsed for ACS.
- **What the graph contains and how it is shown:**
  - File nodes (71) and IMPORTS / INHERITS / INSTANTIATES edges (255), from `ast`.
  - The tool returns 1-hop neighbors in both directions, as `arrow [EDGE_TYPE] repo/relative/path.py` lines plus a total.
  - Bare file paths with edge type and direction only: no symbol names, no signatures, no file:line.
- **What "task completion" means:**
  - ACS ≥ 1.0, meaning every gold file was read or edited. It is a navigation metric, with no tests and no correctness check.
  - The 99.4% vs 76.2% in the listing abstract is mean ACS on G3, not completion.
  - Completion is reported overall only: 54% / 62% / 66%.
- **Adoption numbers:** listed in the adoption table under Results. Only Condition C had the tool.
- **Prompt engineering and its effect:**
  - Original: the task prompt tells the agent to call the tool on the primary file first and to read all returned neighbors. The tool's docstring repeats "use this before editing any file".
  - Revised (G3 only): a mandatory checklist placed at the end of the prompt. G3 adoption rose from 85.7% (30/35) to 100% (31/31), and ACS from 96.6% to 99.4%.
  - Neither prompt's text is published in the paper.
- **Is anything pushed into context?**
  - Only in Condition B: the top-10 BM25 file list is prepended.
  - The graph is never pushed. It enters context only through the agent's own call.
  - So push vs pull here differ in information (BM25 files vs graph neighbors), not just in delivery.
- **Wrong edges or decoys:** none. The risk is only speculated about in §6.4.
- **CIs and statistics:**
  - ± SD per cell, and Welch's t on G3 only, treating trials as independent.
  - No CIs, no paired or task-level tests, no correction.
  - My recomputation reproduces the t values.
- **Same FastAPI as SWE-bench-style tasks?**
  - No. This is nsidnev's FastAPI RealWorld example app, a blogging API that uses FastAPI.
  - The competition's FastAPI tasks come from the fastapi/fastapi framework repo, with symbol-level graphs (`docs/competition.md` lines 75-82).

## What it does NOT do that the idea needs

- Push the same graph facts into context, information-matched to a pull arm.
- Vary presentation: bare names vs names + signature + file:line.
- Plant a wrong edge and measure following against the true-edge base rate for the same target.
- Paired forks from one saved state, scored on the next read or edit target.
- Run a small quantized model under a 16k cap with the competition's graph tools, scoring repair by tests and counting interface failures.
- Separate "tool called" from "information acted on".

**Useful for us:**
- **Cite as motivation, with the confounds.** The 0/30 G2 adoption and 58% zero-call rate are the cleanest published numbers for an agent not querying a code graph it has.
- **Never mandate reading tool output in one arm only.** Their read-all instruction turned the tool's effect into compliance. Our pull and push arms need identical instructions, and the outcome should be the next target, not coverage.
- **Hold instruction position fixed.** Moving the checklist to the end raised adoption from 85.7% to 100% on G3. Text and position must be identical across delivery arms.
