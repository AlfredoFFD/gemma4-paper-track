# RepoAtlas: Guiding Coding Agents via Evolving Multimodal Repository Views

- **arXiv:** 2609.16936 (cs.SE)
- **Authors:** Yunxiang Zhang, Haiquan Wang, Jiawei Guo, Hanyang Xia, Yan Chen (corresponding), Tong Chen, Zhang Zhiwei,
  Junchen Ye. Beihang University, plus one independent researcher.
- **Version read:** v1, 15 Sep 2026. The arXiv API lists no later version as of 2026-10-27. Read from the arXiv HTML
  text and the 9-page PDF.
- **There is no appendix in v1.** The body sends five things to "the appendix" (text lines 253, 293, 343, 490, 501):
  relevance calibration, the selection pipeline and representative exposure, state-transition rules, budget
  sensitivity, and per-run results. The PDF ends at the references, so none of these could be checked.

## Claim

- A training-free module pushes a budgeted code-graph view (one rendered image plus an aligned text index) into a
  coding agent's context, conditioned on the issue and on the agent's exploration state, and refreshes it when that
  state changes. This raises SWE-bench Verified resolve rate and cuts input tokens and model calls for three
  vision-language models.
- **Headline (abstract, §1):** +2.4 points resolve, -5.8% input tokens, -7.8% model calls on average, against the
  strongest multimodal graph baseline. Re-derived from Table 2: these are the means of the per-model margins over
  SeeRepo (+2.3 / +1.1 / +3.8 points; -7.9 / -4.9 / -4.5% tokens; -8.2 / -3.9 / -11.4% calls).
- **Component claims (Table 3, Qwen3.6 only):** the text index matters more than the image (-3.9 vs -1.9 points when
  removed); refresh timing matters (no refresh -4.7, refresh on every call -12.1); the node budget matters (-3.3).
- **Selection claim (Table 4, LocBench, no agent):** PageRank propagation and "representative exposure" both improve
  what a 15-node view contains.

## Method (as far as v1 allows a reproduction)

**Graph (§3).**
- Built offline once per repository snapshot; directed and typed.
- Nodes: modules, classes, callables, variables. Each stores its qualified name, its signature when available, and its
  exact source location.
- Edges: containment, inheritance, calls, imports, overrides, symbol use.
- Construction cites tree-sitter, PyCG and an application-centered Python call-graph method.
- Static only: dependencies registered at runtime are absent (see the §5.4 failure case).

**Exploration state (§3).** s_t = (F_t recently inspected files, C_t relevant entities identified from observations,
G_{t-1} the last delivered view, phase in {Localize, Edit, Test}). It starts empty, in Localize.

**View.** G_t = (V_t, E_t, M_t) with |V_t| <= B_V = 15 and |E_t| <= B_E = 20 (§5.1).
- A node may be a supernode standing for a set of entities.
- M_t is the presentation spec: granularity, aggregation, and the visual and textual form.

**Select (§4.2).**
1. **Direct relevance per node:** the maximum of three scores, after calibration to a common scale (Eq. 1; the
   calibration is in the missing appendix):
   - lexical: issue text vs identifiers and source;
   - semantic: issue vs the entity embedding;
   - trajectory: recent observations.
2. **Propagation:** personalized PageRank over a row-stochastic matrix built from edge-type weights normalized over
   out-edges, restarting from the normalized direct scores (Eq. 2), solved by power iteration. The damping d and the
   edge-type weights are not given.
3. **Final score:** r_t(v) = max(normalized direct score, propagated score).
4. **Region:** pick a connected region that maximizes the summed score under the budget (Eq. 3), approximately,
   adding supernodes when needed. Each supernode exposes its top-scoring member as a concrete node with a source
   location ("representative exposure").

**Project (§4.3).**
- One image whose layout (force-directed, hierarchical, flowchart, others) is chosen from the region's topology and
  the agent's state. The layout-choice rule is not given.
- A text "grounded index" with one row per node: ID, name, type, signature, and location as a file:line range
  (Fig. 2, Fig. 3a). Stable keys tie image nodes to index rows.
- Projection never changes the selected entities or relations, so presentation variants are content-equivalent.

**Refresh (§4.4).**
- **Triggers:** an explicit agent request, or a proactive check after file reads, edits or test feedback.
- **Rule:** keep the last view if it still covers the evidence relevant to the current phase; otherwise re-run select
  and project.
- **Image retention:** only the current image is kept; earlier code locations survive in a compact text index.
- **Localize:** a multimodal view, refreshed when structural coverage becomes inadequate. The issue text is always
  kept as evidence.
- **Edit (after the first substantive edit):** the image is replaced by a focused text view of the modified code and
  its structural impact, refreshed only when the patch scope materially changes.
- **Test:** refresh if feedback changes the inferred impact scope, then resume the previous phase or return to
  Localize.
- The adequacy tests and thresholds are in the missing appendix.

**Agent and runs (§5.1).**
- The scaffold under RepoAtlas is not named.
- Baselines use their official implementations "under matched agent settings", differing only in method-specific
  interface instructions.
- LocAgent runs its localization pipeline to completion; issue resolution then continues with the same settings.
- Methods that need fine-tuning are excluded.
- Each configuration is run three times.
- There is no code link in v1.

## Setting, data, models

- **Data:**
  - SWE-bench Verified, all 500 instances, end to end;
  - LocBench, all 560 instances, for selection only (no agent).
- **Models:**
  - Qwen3.6-35B-A3B: self-hosted, the only open-weight model, and the model used for every ablation;
  - MiMo-V2.5 (API);
  - Kimi-K2.5 (API).

  All three are vision-language models, because the method needs image input. MiMo's and Kimi's sizes are not stated.
  No quantization is reported.
- **Context:** no limit is stated. Dividing Table 2's input tokens by its calls (my arithmetic) gives a mean input per
  call of 18.0K tokens for Qwen, 15.3K for MiMo and 17.2K for Kimi under RepoAtlas. These counts include image tokens
  and count cached tokens in full. The prompt accumulates, so peak context is above these means.
- **Baselines:**
  - mini-SWE-agent (text only);
  - LocAgent (graph-guided textual search and traversal);
  - SeeRepo: text tools plus agent-requested renders of a query-centered subgraph, where the agent names a node, an
    edge type and a depth.

## Metrics (exact definitions)

- **Resolve (%):** the SWE-bench Verified resolution rate.
- **Input tokens, output tokens, model calls:** per-instance means over complete trajectories. Input includes image
  tokens and counts cached tokens in full.
- **API cost ($):** provider list prices with cache discounts; Qwen is priced at a commercial endpoint's list rate.
  Token and cost numbers compare only within a model.
- **LocBench (Table 4 caption):**
  - FA@k counts an instance correct only when every gold file is among the first k files of the view.
  - FR is recall over gold functions, crediting only those shown as concrete nodes.
  - AC is the share of gold functions whose file is reachable from a concrete code location among the first five
    files.
- **Case study:** the step at which the gold file is first opened (median across runs), model calls, and runs
  resolved.
- **Uncertainty:** there are no standard deviations, confidence intervals or tests anywhere.

**Case studies (§5.4, Fig. 3).**
- **sympy-18698 (success).** The issue names no file. Four same-named `sqf_list` implementations sit in three modules.
  The fix is in `_symbolic_factor_list`, an unmentioned helper two calls below the entry point, and it is not in the
  first view.
  - RepoAtlas opens polytools.py at step 2 (the agent's message says the graph view pointed it there), reads the gold
    function at step 6, and makes its first edit at step 17.
  - SeeRepo goes to sqfreetools.py first, reaches polytools.py at step 11, and is grepping tests after step 21.
  - Across runs: gold file first opened at a median step of 2 vs 7; 47.5 vs 66.3 calls; resolved 3/3 vs 0/3.
- **sympy-17630 (failure).** The traceback points at blockmatrix.py. The fix is in matexpr.py `_postprocessor`, a
  dependency registered at runtime and therefore missing from the static graph.
  - In eight runs across the three models, RepoAtlas never opens the gold file, and refresh keeps narrowing the same
    wrong region.
  - A text baseline solves one run, after reaching matexpr.py at step 30.

- **Fig. 1 (p.1, schematic, no data).** Three agent types on a toy "fix the breakdown bug" repo:

  - (b) a textual-graph agent reads linearized node and edge lists: correct patch, highest cost;
  - (c) a multimodal agent gets a typed graph image (module/class/callable/variable; contains/calls/import/uses) and a

  The coin counts are illustrations, not measurements.

  - B. Adaptive projection: the same structure drawn force-directed, hierarchical or as a flowchart, plus a
    Name/Type/Signature/Location table.
  - C. State-aware refresh: reuse vs refresh after a file read, code edit or test feedback, or on explicit request.
  - The agent loop: build context (issue, history, current view), reason, act (search/read/edit/test), update state.

## Limitations

**The authors'.** The static graph misses runtime dependencies (the failure case and §6). They plan to add dependencies
inferred from execution traces and test feedback, more projection forms, and other repository-level tasks. The paper
has no limitations section.

**Mine.**
1. **No uncertainty at all,** and the per-run data are in an appendix that v1 does not contain.
   - My rough noise band for a resolve difference on 500 shared instances: a 95% half-width near 2.8-3.9 points if
     10-20% of instances are discordant between arms (paired), and near 6 points unpaired. This is my estimate, not
     the paper's.
   - Every margin over SeeRepo (1.1-3.8 points) and the visual-channel ablation (-1.9) sit inside that band.
     Per-call refresh (-12.1) does not, and no refresh (-4.7) probably does not.
2. **Push vs pull is confounded with everything else.** SeeRepo and RepoAtlas differ in graph construction,
   selection, rendering, budget and prompt instructions. No arm offers RepoAtlas's own view only through a tool.
3. **The baseline behind each margin changes** by metric and by sentence (see Results).
4. **Not reproducible from the paper.** The calibration, d, the edge-type weights, the connected-region search, the
   layout rule, the refresh adequacy tests and phase detection are all deferred to the missing appendix. There is no
   code link.
5. **Weak evidence of use.** The evidence that the agent used the view is its own message, from one instance.
6. **The token-savings explanation is not isolated.** "Bounded context management" is offered as the reason, but mean
   input per call is unchanged against the text-only baseline; the savings track the call count.
7. **Run count.** "Eight runs spanning all three models", where three runs times three models makes nine. Not
   explained.
8. **Contamination.** SWE-bench Verified contamination for 2026 models is not discussed. It would affect all arms
   alike, but would compress the differences between them.
9. **A tension with SeeRepo it does not address.** SeeRepo's own abstract (v4, ASE 2026; I read the abstract only)
   says visualization helps most when the agent itself controls exploration depth. That sits in tension with
   RepoAtlas's case for controller-pushed views.

## Assumptions the paper does not test

- **That the gains come from the graph's structure,** rather than from pushing a short list of likely locations early.
  No arm pushes the same 15 locations as a plain ranked list; the nearest, the index-only arm, has no edges and
  scores 61.2.
- **That a pushed view is harmless when it is wrong or incomplete.** Most views omit the gold function (FR 0.252), yet
  outcomes are not split by whether the view contained the target, and nothing is planted.
- **That the same content would be used less if it were only queryable.** This is inferred from SeeRepo's 40.5%,
  never tested on the same content.
- **That images distract during editing.** The text-only switch at Edit is taken from SeeRepo, not ablated here.
- **That results hold** for a non-vision model, a small context window, or a quantized model.

## Overlap with the idea, component by component

**C1 Setting: partly.**
- It does end-to-end issue repair on SWE-bench Verified, with a code graph pushed into the agent's context, and one
  model is open-weight and self-hosted (Qwen3.6-35B-A3B, 3B active).
- But the graph is the paper's own (with signatures and file:line), the models read images, nothing is quantized,
  and there is no hard context limit.

**C2 Delivery: partly. In detail:**
- **What is pushed:**
  - a guaranteed turn-1 view: one image of at most 15 nodes and 20 edges, plus index rows with ID, name, type,
    signature and file:line range;
  - refreshes by the controller on state change or on agent request (2.43 views per instance);
  - after the first edit, a text-only focused view.
- **What is pulled:**
  - SeeRepo's renders of a neighborhood the agent specifies (node, edge type, depth), obtained in only 40.5% of
    instances in this paper's reproduction;
  - LocAgent's textual search and traversal tools, run as an upfront localization pipeline;
  - RepoAtlas also accepts agent requests on top of what it pushes.
- **Is the content the same?** Not between the push and pull arms: graph, selector, renderer, budget and instructions
  all differ. Yes within RepoAtlas's own projection ablations, which hold the selected entities and relations fixed
  and vary only modality and layout. All of those arms are pushed.
- **Presentation** (closest to the idea's bare names vs names + signature + file:line), on Qwen3.6 (Tables 2-3):

  | Arm | Resolve |
  |---|---|
  | Image with node names only | 59.2 |
  | Index rows with name, type, signature and file:line, no edges | 61.2 |
  | Both | 63.1 |
  | No graph | 60.8 |

  On LocBench, hiding the concrete representative node and its source location drops FR from 0.252 to 0.102 and AC
  from 0.494 to 0.343.
- **Budgets:**
  - 15 nodes and 20 edges per view (the sensitivity analysis is in the missing appendix);
  - the token size of a view is not reported;
  - no context cap;
  - mean input per call of 15.3-18.0K tokens (derived).
- **Models:** Qwen3.6-35B-A3B, MiMo-V2.5, Kimi-K2.5.
- **Effect sizes, push minus pull (RepoAtlas minus SeeRepo):**
  - +2.3 / +1.1 / +3.8 resolve points;
  - -7.9 / -4.9 / -4.5% input tokens;
  - -8.2 / -3.9 / -11.4% calls.

  No uncertainty is reported. By my estimate these fall within paired noise on 500 instances.

**C3 Truth: not covered.**
- Nothing is planted, and there is no base rate.
- The one observation is the sympy-17630 failure: a graph missing a runtime edge kept the agent away from the gold
  file in 8 of 8 runs, while a text baseline found it once. That is an incomplete graph steering the agent:
  anecdotal, and without a base rate.

**C4 Method: not covered.**
- Whole trajectories are run independently, three runs per configuration, with no saved-state forks.
- The case study's "step at which the gold file is first opened" is a next-read measure we could adopt.

**C5 Claim: partly.**
- The paper argues that a guaranteed view beats an on-request one (40.5% uptake, which by its account leaves most
  trajectories without repository context). That supports "visible beats queryable", but without a controlled test.
- It uses the agent's own stated reason as evidence of use, which is the kind of evidence C5 says is not enough.

**C6 Cross-domain: not covered.**

## What it does NOT do that the idea needs

1. Hold content fixed while changing delivery: the same view pushed vs available only through a tool.
2. Plant a wrong-but-plausible edge, and score following against how often the agent visits that target under the
   true graph.
3. Fork from one saved agent state with a shared prefix and seed. Because it compares whole trajectories, the view's
   effect on the next read or edit cannot be isolated.
4. Run a small, quantized, text-only open model under a hard context cap. Every model here reads images, and no cap is
   set.
5. Use the organizers' graph and tools, whose output is names only (per this repo's notes).
6. Report uncertainty or paired tests: no McNemar test, no CIs, no per-run data.
7. Count interface failures (edit mismatches, overflow, malformed patches) separately.
8. Anything outside coding agents (C6).
